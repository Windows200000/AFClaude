# AFClaude

> **⚠️ AI-generated.** All code and docs in this repository were written by Claude (Anthropic's Claude Code, model Claude Opus 5.5), running mostly unattended ("AFK") on the owner's server. A human set the goals and the rules and reviews the results, but did not write this code. Treat it as a prototype.

AFClaude keeps long-running Claude Code sessions going while nobody is at the keyboard. When a session hits its usage limit, AFClaude waits for the reset. Then, inside a nightly window and only if the weekly budget allows, it continues that same session. It is the first building block of a planned cross-session task system, in which every project is run by one Claude session, its *task-manager* ("manager" is reserved for a user role, see `docs/dashboard_design/02_users_roles_and_access.md` §2).

## Rules

- **The core AFClaude session always runs on Opus 5.5 (`claude-opus-5-5`) with `--effort high`.** Subagents it spawns may use other models (e.g. Haiku for cheap classification). `keepalive.py` and `ka_resume.sh` default to exactly that.
- Permission modes for unattended runs (nothing may hang waiting for a human): main sessions `--permission-mode auto`, plus narrow per-launch allow rules (`ka_resume.sh`, `claude agents`) that are checked before the classifier. Haiku and other models without auto mode use `dontAsk`; so do all `claude -p` helper calls.
- Sessions launched by AFClaude get the guard-hook bypass (`CLAUDE_GUARD_DISABLE=1`) so they never hang unattended. They are told to read the guard hooks and respect them anyway.

| `keepalive.py` | Runs the AFClaude task-manager. **Runs begin only at starts (D-205)**: each session-window start of the night window and each last-stretch slot start; the budget rule decides there and a passing start continues the task-manager, which works its own tasks (today only AFClaude has a task-manager; picking among several by rank/priority is design phase 3b). **No continue after a session limit (D-204)**: the watcher reads the session's transcript, detects the synthetic "You've hit your … limit" notice and parses the reset time, but only logs it (`LIMIT_HIT`, one PROGRESS note per stall): a limit hit is the job done for that run, nothing continues it at the reset; the next session-window start (or last-stretch slot start) decides by its own check, and may find the run stopped at a limit (e.g. limit before 04:00, next run at 04:00; a start whose session limit has not reset yet waits for it). Dry-run unless `--arm`. `--window-start` is a one-shot "continue at a session-window start" (D-202/D-203): a window is N × 5 h session windows (23:00 and 04:00 for 23:00 × 2; 23:00 and 03:00 CET / 05:00 CEST on the DST nights, D-148) and the gate is checked at the start of each, never in between. A failed request, a failed reading after it or a window that didn't open is only logged (an ERROR line in the app log + its record; no alert, no pause: D-280, the owner's exception to D-235); the start's decision is already stored. If the budget rule postpones it (the user was active), the running watcher re-decides it at the recheck time (`keepalive_deferred.json`), but only before the night's next session-window start, so its run still ends by the window end; a later recheck (and any postponement at the last start) is skipped to the next session-window start. The watcher also continues the session once per last-stretch slot, at the slot start (never at a limit reset in between). `evaluate()` is the continue decision for the owner's approved stalled sessions (reset + grace, no window, no budget gate; the dispatcher's, D-206). `--decide` prints the current decision. **Run end (D-224):** a run ends at the earliest of the task-manager's clean stop (`--run-stopped`, its last step; recorded in `run_stops` of the keepalive state in the DB, also when run on the host; a DB it can't write fails the command, the stop kept in `data/ALERTS.fallback.md`), a limit hit, 15 min without a transcript write (`RUN_IDLE`) and its session window's end; the owner's own messages never end a run, and after a stop they no longer keep it going (`run_active()`, `run_metrics.py`'s `end_reason` "stopped"); a later fire starts a new run. `--now` (with `--window-start`) skips the start-hour gate (budget rule still applies). `--work-on` starts a backlog project. `--session-rules manager|afclaude` is the repo's `SessionStart` hook (D-225, see Permissions): it injects the standing rules at session start, on resume and after every compaction, so the continue messages to the task-manager (`continue.md`, `fillup.md`, `last_mile.md`, + the hand-off after a compaction) carry only the budget line, the PROGRESS pointer, the run specifics and a one-line pointer to those rules (~0.5–1 k characters instead of ~9.3 k). The watcher also fires the fill-up run of a run that ended early (D-212, see `fillup.py`), and it sleeps until the next due time (a fill-up start, a last-stretch slot start, a postponed start's recheck) when that comes before its 30-s poll, so these fire within seconds of their time. **Compaction (D-144/D-233/D-238, design §5.5):** the watcher (`compaction_pass`, once a minute) compacts the task-manager while its prompt cache is still warm: right when a run has ended (D-224; the session's last prompt was the run's, not the owner's) and after 50 min without a request (before the 1-hour cache expires; this also covers the owner's daytime chats), only if its context is at or above the setting `compaction_threshold_tokens` (D-307, 150k; it replaced the break-even computed from the stored cost model, `compact_timing.py`, ≈177k with the built-in one, which the records and the quickview still show). **Mid-run (D-307):** during a run, once the context passed that threshold, at the next idle point (no turn or subagent running, the owner not typing; not within 60 min of the last compaction, only once the context was below the threshold since it, not within 10 min of the owner's message): the same save → `/compact` flow, then `prompts/compact_after_run.md` instead of the READY message (the run goes on: its start, the budget evaluated now, the window end from the fire record's `run_end`, the pacing); a mid-run compaction is no run end (`run_active`). Never at a start any more (D-191/D-218's age rule is gone); a start (the cron's window-start) waits for a running compaction (a per-session file lock) up to 40 min, then is aborted. Held (logged once, not an error) while a run uses the session (except mid-run), a turn or a subagent is running, the owner is typing (an attached terminal with keystrokes in the last 10 min, a draft in the input box or a dialog open: `tmux list-clients` / `capture-pane`; the box's top border may carry the session's title; a pane showing neither the input box nor a dialog is an error, D-235), the owner holds the session elsewhere (preflight), it isn't live in its tmux session, it stopped at a limit or its session limit is above 97%, or a start that types into it is due within 40 min. Steps (`keepalive.compact_with_handoff()`, the live test runs it): the save prompt `prompts/session_end_save.md` and a new hand-off in the DB (≤ 10 min, D-233), `/compact <prompts/compact.md>` and its marker in the transcript (≤ 10 min), then `prompts/compact_after.md` with the hand-off (`compact_resume.md`): the session answers READY without starting work, the hand-off is consumed. Every attempt (and a context above the break-even whose cache expired without one: "missed") is recorded in the keepalive state's `compactions` (one per activity, never retried); any failure or timeout on the way is an error (D-234/D-235: recorded, alerted, automation paused). ## AFClaude container (docker/)

The container runs AFClaude's schedule and code, while everything that touches Claude sessions still runs on the host, through a strict SSH bridge.

- **Image** (`docker/Dockerfile`, `python:3.12-slim`): python3, supercronic (non-root cron), openssh-client, tini, procps, the MCP SDK, plus git/tmux for the unit tests only. It runs as UID/GID 1000 with `HOME=/home/opc`. The code is baked in at the host repo's own path, owned by root, so host-facing paths (cwd, PROGRESS.md in messages) stay the same.
- **Schedule**: `docker/crontab` mirrors the host's AFClaude crontab lines (sampler, window-start, watcher watchdog, usage review, quickview export, dispatcher, docs import, log retention), plus (phase 3a S2-S7) the runner watchdog `runner.py ensure`. With `AFCLAUDE_SCHEDULER=on` the entrypoint also starts the resident runner (`runner.py serve`) beside supercronic and stays as their parent: a `docker stop` reaches it through tini, and it passes the SIGTERM to supercronic and to the runner (`runner.py stop`, which waits for its clean exit; compose `stop_grace_period: 90s`). supercronic's job-start lines are also copied to `data/cron_runs.log` (for `runner.py shadow-report`). `AFCLAUDE_SCHEDULER=legacy` is the rollback: supercronic with `docker/crontab.legacy` (the crontab before the runner, frozen at S2), the watcher and the inbox API, no runner; switch with `docker/.env` + `docker compose up -d` (no rebuild). The entrypoint starts the watcher right away (`docker/start_watcher.sh --boot`, the counterpart of `start_keepalive.sh`; it replaces the `@reboot` line): retried every 15 s until it runs (the bridge may need a moment after a rebuild), for up to ~15 min, after which the :07/:22/:37/:52 watchdog line keeps trying; never while `PAUSED` exists, never a second one (a lock file serializes the entrypoint's and the watchdog's starts, and `keepalive.py`'s own lock stops any second instance). So after `docker compose up -d --build` the watcher is back within seconds, not at the next watchdog. `at` is a shim (`docker/at_shim.py`) that stores the sampler's pre/post-reset jobs (and one-off reviews) in the DB (`scheduled_jobs`), run by a per-minute cron line (the old `data/at_spool/` is read-only legacy). `AFCLAUDE_SCHEDULER=on|legacy|off` (default off: the container only idles).
- **Inbox API**: `inbox_api.py serve` (the message box's endpoint and worker, D-241) is started by the entrypoint (`ensure --boot`) and kept up by a */5 cron watchdog (`ensure`, one alert per outage). It listens on the unix socket `data/api/inbox.sock` (the quickview's nginx connects to it), never on a port, and reads the quickview key from `~/.config/afclaude/quickview.key` (mounted read-only at `/run/secrets/afclaude_quickview.key`).
- **Mounts** (no docker socket, no privileges, no ports, read-only root fs): the host repo read-only at `/host/repo`. PROGRESS/ALERTS/OPEN_QUESTIONS/BACKLOG/GOALS/EXCEPTIONS/README/DECISIONS and PAUSED are symlinks to it, so reads are always fresh. `data/` is read-write. `~/.claude/projects` and `~/.claude/sessions` are read-only, plus the bridge key and the host's public ed25519 host key (for strict checking). `~/.claude.json` is **not** mounted: claude replaces that file, so a file bind mount would go stale. The usage cache comes via the bridge. Watcher lock, log and STOP are in `data/keepalive/` (its state is in the DB).
- **Bridge**: `host.py` runs `ssh opc@host.docker.internal` (host-gateway, `extra_hosts`) with the key from `install_host_bridge.sh`. The compose network is pinned inside `172.16.0.0/12`, which the key's `from=` requires. sshd runs `docker/host_exec.py` as a forced command, which accepts only its whitelist. Host behaviour without `AFCLAUDE_IN_CONTAINER` is unchanged.
- **Machine-specific values**: `docker/.env` (gitignored; template `docker/env.example`).
- **Deploy**: `python3 tools/deploy.py` is THE deploy command (D-257) — drain, wait for the container to go quiet (no sampler / usage-review / unittest / bridge `claude` call in flight, D-234/D-235), then rebuild with `AFCLAUDE_CODE_VERSION=$(git rev-parse --short HEAD)` baked into `CODE_VERSION` (the code version `prompt_defaults` records; the image has no `.git`, so without it the version is unknown). Never run the bare `docker compose -f docker/compose.yml up -d --build` directly: a rebuild replaces the container outright and can cut an in-flight bridge call, which the 21.10. incident showed can wedge the usage cache stale for several minutes. Unit tests inside: `docker exec -e AFCLAUDE_IN_CONTAINER= afclaude python3 -m unittest test_keepalive` (the tests use local stubs, so the bridge is switched off for them).
- **Dev override** (code from a checkout, read-only, no rebuild): `AFCLAUDE_DEV_SRC=/path/to/checkout docker compose -f docker/compose.yml -f docker/compose.dev.yml up -d`.
- **MCP server from the container**: `docker exec -i afclaude python3 /mnt/BlockVolume/Claude/work/AFClaude/mcp_server.py` is a drop-in stdio command (e.g. `claude mcp add --scope user afclaude -- docker exec -i afclaude python3 …/mcp_server.py`). The existing registration (host `.venv`) keeps working. Both use the same `data/afclaude.db`.
- **Stop / pause the container watcher**: `touch data/keepalive/STOP` (the next start removes it); `touch PAUSED` in the host repo keeps it stopped. `start_watcher.sh` never starts a second watcher while one runs on the host (a `keepalive.py --session` process without a one-shot flag; the */30 `--window-start` run or a `--plan-fillup-test` call is none).

## Budget rule

Goal: use the whole weekly limit (about 100% at each weekly reset) with autonomous work, without ever getting in the user's way. AFClaude runs begin only at starts (D-205): each session-window start (23:00 and 04:00 for 23:00 × 10 h, generally start + k × 5 h; D-202/D-203) and each last-stretch slot start. There is no continue after a session limit (D-204): a full session is the job done for that run (ideally the task-manager stops before it fills), and the next start decides by its own check. Every start asks `keepalive.budget_eval()` (`budget_decision()` / `budget_headroom()` wrap it): the window-start pass and its postponed recheck, the last-stretch pass, `--work-on`, `--decide` and the quickview. The owner's approved stalled sessions are not AFClaude runs: the dispatcher continues them at their reset without this rule (D-206). So they all show **the same number**, the "budget for this run" (weekly %, also ≈ session windows): the decision reason, `budget_headroom()`, `--decide`, the continue message and the quickview tile carry it. The `usage_model` setting selects the model: `"pacing"` (default, `pacing.py`) or `"linear"` (the original rule). If `pacing.py` raises, the original linear rule decides (the reason says so), except inside the last stretch, which then holds: the linear rule cannot see the user.

### Pacing (`pacing.py`, default): the original linear rule, forecast-driven night gate

The original rule filled the week gradually along a straight line (continue while weekly % < 90 × elapsed / 7 d). Pacing keeps the gradual fill but decides with a forecast of the user's own use, in full session windows only (owner decision 04.10.2026):

```
threshold     = the reserve_threshold setting: "auto" (default) = one session window left
                = 100 − full_session_cost, full_session_cost = 100 × ratio (now ≈ 15.4 → ≈ 84.6%);
                or a % override (50..99; a legacy week_target counts as the override)
At every decision (each session window of the night is re-checked):
    w             = weekly % now
    run_cost      = ratio × (100 − session %) of the live session window, else full_session_cost
    predicted_end = w + run_cost + forecast(now → weekly reset)
                    forecast = the user's other use + the owner's design chats (D-266)
    RUN a full session window iff predicted_end ≤ threshold; budget for this run = run_cost
    otherwise no run (no partial runs); the next session-window start re-checks
    checked only at each session-window start of the night (23:00, 04:00; D-202), never in between
    without a forecast: the straight line, RUN iff w + run_cost ≤ threshold × elapsed at tonight's window end
The model has no margin: the threshold is the only spare.
CONTINUE also needs the user idle and the session < 85%.

Last stretch: the final min(ceil(sessions_left), 2) × 5 h before the reset,
    sessions_left = (100 − w) / (100 × ratio), ratio = limit_ratio.preferred_ratio() (0.2 if too little data):
    budget 100 − w, session cap 100%.   last_mile_hours: "auto" (this) or a number of hours (0 = off).
```

- **The forecast** (`fit_profile()` / `forecast_user()`, no margin) blends two estimates of the user's use until the reset:
  - the **rate forecast**: the user's typical weekly-% rise per hour of the week (Berlin weekday × hour) from the last 4 closed weekly cycles, each hour's rate shrunk toward the mean rate with `shrink_hours` pseudo-hours (`(rise + m × mean) / (hours + m)`; with a few weeks, one busy hour of one week no longer becomes the forecast for that hour);
  - the **weekly budget**: the user's typical weekly total (per closed cycle: its final weekly % minus AFClaude's own rise in it, the mean over the cycles with a final reading) minus the user's use so far in this cycle (weekly % now minus AFClaude's rise), spread over the rest of the cycle in the shape of the rate forecast;
  - forecast = (1 − `budget_weight`) × rate forecast + `budget_weight` × budget left (without a closed cycle with a final reading or a reading of the open cycle: the rate forecast alone).

  The defaults (`shrink_hours` 24, `budget_weight` 0.5) are `pacing.PREDICTOR_DEFAULTS`; the user model's optional `predictor` object (`python3 telemetry.py user-model get`, written by the usage review) overrides them per user, and an invalid value is an error, not a fallback. AFClaude's own runs are left out of the user's use: the recorded runs (`run_metrics`, start to end, the split `limit_ratio`'s week share uses), and for a fire without a run row the span from the fire until the next prompt in an AFClaude session or the run going idle. Below 72 covered hours the straight line is used, and the reason says so.
- **Design chats** (D-266, D-264): the owner's own chats with the task-manager outside runs are AFClaude usage, tracked as their own category. The rise outside runs is split per sample interval by the weighted tokens of AFClaude's own sessions vs the other sessions (`own_w_tokens` / `other_w_tokens`, as `stage_eta.py --split`; no local tokens = another device = other use). The rate forecast and the weekly budget above are the user's **other** use only (`forecast_user()`; a closed cycle's weekly total counts only if the samples cover ≥ 80% of it, since the unsampled rest can't be split). The design chats are forecast as a steady weekly amount (`forecast_design()`): the trailing mean of their measured rise per covered hour over the same closed weeks (D-264: flat until ≥ 4 measured weeks exist), spread evenly; inside the open week blended like the weekly budget (`budget_weight` × the week's amount minus the design chats so far). The night gate still adds both (`forecast_gate()`), so the owner stays protected (D-141/D-258); the reason, `--decide`, `threshold_info()` (`forecast`: per week; `now`: until the reset) and the quickview show them apart. The model error (backtest, forecast log) is scored on the sum, the use outside AFClaude's runs.
- **Its accuracy is computed in code, not tuned by hand.** `pacing.forecast_backtest()` back-calculates the forecast's error from the usage data: at every past night session-window start, it fits the forecast on the samples up to that point (what the gate would have used: the closed cycles and the use so far in this cycle) and compares it with the real use outside AFClaude's runs (other use + design chats, what the gate adds) until the reset (until now for the open week). `pacing.ratio_stats()` gives the session/weekly ratio's spread over the session windows (`limit_ratio.py`). `pacing.threshold_info()` combines them: ratio ± spread, full-session cost ± uncertainty, the model's bias / sd / rmse (n, how many points reach the reset), the predicted week end's uncertainty, the dynamic default and the active threshold with its source. `--decide`, `python3 pacing.py` and the quickview show it. Armed window-start decisions are also logged to `data/forecast_log.jsonl` and `pacing.forecast_errors()` scores them once the week has closed.
- **The run's own use doesn't flip the gate mid-session**: as AFClaude works, w rises and the rest of the session window shrinks together, so the predicted end stays the same. A daytime decision (`--now`, `--work-on`) uses the same gate.
- **User activity** (yield): only turns or prompts in non-AFClaude sessions (`activity.other`) and a weekly-% rise without any local turns (another device or claude.ai). The user's own input to AFClaude sessions does not count. Missing or stale (> 30 min) sampler data counts as active.
- **A HOLD for the user postpones**: recheck at last activity + `idle_min` (60 min), then fire if still allowed. A postponed session-window start is kept in `keepalive_deferred.json` and re-decided by the watcher under the same once-per-start key, only until the night's next session-window start (a run started later would end after the window end; D-202), else it is skipped to that start. Unknown activity or usage: recheck after 15 min; session guard: at the session reset. Not in the last stretch (D-259): it runs regardless of the owner's activity (`last_mile_yield`, default false, turns the yield back on there). A last-stretch start (a slot, a window start or a fill-up in it) still never types into a session the owner is typing in or holds: while the owner holds the session (Remote Control, another process) or is typing into its tmux pane (keystrokes in an attached terminal in the last 10 min, a draft in the input box, a dialog open) the start waits and is retried every 5 min, instead of being skipped.
- **The last stretch** is continued once per session slot by the watcher (`last-mile-<reset>-s<k>`), at the slot start; a run that ends at a limit inside a slot is not continued at the reset, the next slot start decides (D-204). The session cap is 100% there. The watcher wakes at the slot start (within a second or two), also while an earlier slot's HOLD recheck is pending.
- **The fill-up run (D-212)**: a run that ended early (the task-manager stops at `session_stop_pct`, 95%) is continued once more shortly before its session reset, at reset − (100 − session %) / measured fill rate × `fillup_factor` (110%), to use the rest of the session window; it is the owner's one exception to "runs begin only at session-window starts" (D-202): it continues the run's own window and never opens a new one. Skipped when `fillup_enabled` is off, after a limit hit, outside the night window and the last stretch, when a session-window start before the reset continues the window anyway, or when its weekly cost (remaining × the session-to-week ratio) is more than what is left of the run's budget; it waits while the run is still going and yields to an active owner (in the last stretch only to the owner typing into or holding the session, D-259). See `fillup.py`.

Its yield / guard parameters are DB settings: `pacing_idle_min` (60), `pacing_min_gap` (1), `pacing_session_cap` (85), `pacing_last_mile_yield` (false, D-259) (until phase 2a overrides in the user model, imported once; the retired `forecast_margin` is ignored). `python3 pacing.py` prints the current decision and `threshold_info()`; `python3 keepalive.py --decide` adds the last-stretch period and postponed window starts. `tools/budget_backtest.py --reset <ISO> --user-until <ISO> [--threshold auto|<pct>]` replays one weekly cycle of `data/samples.jsonl` for the original linear rule, the retired reserve model (`usage_model.py`, kept only for this comparison) and pacing with the straight line and with the forecast (end-of-week %, min/p10 user headroom, blocked user demand, AF-caused session hits, nights with work, forecast error).

### Linear rule (`"usage_model": "linear"`, and the fallback)

1. in the last stretch (`last_mile_hours`, "auto" as above) → continue up to 100%
2. projected end-of-week usage < 90% → continue (linear extrapolation over the elapsed week, elapsed floored at 24 h)
3. otherwise, continue only if the weekly reset is ≤ 11:00 Berlin after the current window
4. otherwise, hold

## Stage ETAs

Owner decision D-213: like the usage prediction, predict when each project stage is done, cumulative (this stage in 3 days, the next in 4, the one after in 6, …), with a rare review. The owner's formula: *sessions required / (total available − user usage)*; the usage prediction supplies the second part, so the only new estimate is how many session windows a stage needs.

- **Sessions required** per open stage (a task of the task store, in execution order: priority level, project rank, stage): its own `estimated_sessions` (a task column, written through actions.py: `tasks.py edit ID --sessions N`, MCP `afclaude_update_task(estimated_sessions=…)`; the task-manager may set it, D-185), else the median session windows of the finished stages (AFClaude's runs in `data/afclaude_runs.jsonl` and the owner's design chats, D-264: a stage's cost = run + design-chat usage within its started..done window, each spread over the stages in progress at the time; a stage started and done within 30 min has no measurement; from 3 measured stages on), else `FALLBACK_SESSIONS` = 1 session window per stage.
- **Capacity**: pacing's own pieces, not a second model: at every session-window start of the night windows until the weekly reset the gate passes iff the weekly % then (now + the user's forecast use until then + AFClaude's earlier runs) + one session window's cost + the user's forecast until the reset ≤ the reserve threshold (D-141, D-202/D-203; the straight line without a forecast); the last stretch fills what is left (D-020); later weeks the same from 0%. A session window costs ratio × 100 weekly % (`limit_ratio.preferred_ratio`). The gate's forecast is the user's other use + the design chats (as pacing's gate), and the design chats are AFClaude capacity too (D-266): their steady weekly % / the session window's weekly %, one "design" slot at the end of each day.
- **ETA**: the cumulative sessions laid onto those slots in order. The summary rate (the tooltip) is a typical full week's capacity / 7, shown next to the owner's formula as written, (100 − the user's other forecast week) / the session window's weekly % (design chats are AFClaude's, D-266); the tooltip splits it into night + last stretch and design chats. No capacity in a typical week, or unknown usage, gives `?`.
- **Shown** on the quickview's Progress section (each open phase chip and stage: `~3 d`, `<1 d`, `?`; the tooltip has the assumptions). `export_quickview.py` also logs one prediction per day (the DB, `stage_eta_log`).
- **Rare review**: `prompts/stage_eta_review.md` runs in the monthly usage review (`usage_review.py`): it scores the log (`stage_eta.py --score`: bias, mean absolute error, overdue stages) and improves only the stages' session estimates (D-142 analogue); a better default is code on its review branch, the formula/capacity/order are proposals for the owner.

## Task-manager mode

Every continue/start message ends with `prompts/manager.md`: the controlling Opus session acts as the project's task-manager and hands concrete work to subagents. It's based on the Claude Code docs: best-practices "Use subagents for investigation" ("Since context is your fundamental constraint, use subagents to keep research out of it…") and workflows "When to use a workflow" (Claude as the orchestrator that only receives final results).

| `Bash(python3 keepalive.py --run-stopped:*)` | the task-manager's last step when it stops cleanly: records the stop (`run_stops` in the keepalive state, in the DB), which ends the run for the runner and the quickview (D-224) |
| `Bash(python3 usage_report.py:*)` | the per-session usage table the task-manager records after each subagent (`--last --record`) |
| `Bash(claude agents:*)` | read-only: lists the Claude sessions (also passed per launch, below) |
| `mcp__afclaude` | the AFClaude MCP server's tools (`afclaude_handoff`, `afclaude_ask`, the task tools); the server itself refuses session decisions and standing rules to AFClaude-run sessions |

The same file also sets **`enabledPlugins`** (`commercial-legal@synced`, `product-legal@synced`, `regulatory-legal@synced`, `legal-builder-hub@synced`, each `false`) and **`disableClaudeAiConnectors: true`** (D-307 item 5): these legal plugins and the claude.ai connectors (Gmail, Calendar, Docs, YouTube, Spotify, Strava, PubMed, …) are unrelated to AFClaude and cost context (skill/tool listings, server instructions) in every session; measured ≈37.1k cached input tokens for a trivial headless call before, ≈28.4k after (≈23% less). Only `afclaude`'s own MCP server (user-level, below) and the tools/skills the repo's own prompts use are kept. Same scope note as above: this only takes effect for a session whose working directory is the repo root (every AFClaude launch path resolves to that — `ka_resume.sh` always gets an explicit `--cwd`, and `fire()`'s default for a brand-new session is `HERE`); the narrow headless calls in `keepalive.POKE_ARGV` and `notify.push()` run with `cwd=data/` instead and so don't pick up this file, but they already pass `--tools=`/`--strict-mcp-config`, which bounds their own cost independently.

The same file registers one **`SessionStart` hook** (D-225; matcher `startup|resume|compact|clear`, so it also runs right after every compaction; Claude Code never runs it for subagents): two commands, `python3 "$CLAUDE_PROJECT_DIR/keepalive.py" --session-rules manager` and `… afclaude`, each print one part of the task-manager's standing rules as `hookSpecificOutput.additionalContext` (part 1 `prompts/manager.md`; part 2 `manager_afclaude.md` with `{session_stop_pct}` filled from the setting, `guard_respect.md`, `afk_rules.md`). Two parts because Claude Code caps each hook's context at 10,000 characters. Only a session whose cwd is the repo root gets them (the task-manager and the owner's interactive sessions there, which are the task-manager too); anything else gets no output, and a problem never fails the hook (exit 0; if the rules can't be built, the context names the files to read instead). Continue messages to a session in the repo root then carry only a one-line pointer (`prompts/rules_pointer.md`) instead of repeating the rules; sessions elsewhere still get them inline.

**Per launch, in code (`ka_resume.sh`), not in any settings file:** every session AFClaude starts or resumes gets `--permission-mode auto` (Opus/Sonnet: the classifier judges, nothing hangs) or `--permission-mode dontAsk` (Haiku and other models without auto mode: anything not allowed is denied), `--allowedTools=Bash(<repo>/ka_resume.sh:*),Bash(claude agents:*)` (it may start/continue sessions through this script and list sessions; absolute path, computed at launch) and the env `CLAUDE_GUARD_DISABLE=1` (the guard-hook bypass, see Rules). `claude -p` helper calls use `dontAsk`. These need no install step. Starting sessions (`ka_resume.sh`) is deliberately not in the project settings: there it would also apply to the owner's interactive sessions in the repo.

**User level, installed by the user once per host (not expressible as project settings, and AFClaude never edits a user's config):**

1. **MCP server** (`mcp_register.md`): `python3.12 -m venv .venv && .venv/bin/pip install mcp`, then `claude mcp add --scope user afclaude -- <repo>/.venv/bin/python <repo>/mcp_server.py` (user scope, so sessions in every project can report to AFClaude). Check: `claude mcp list`.
2. **Delegation reminder hook** (`hooks/delegation_reminder.py`, a `UserPromptSubmit` hook; adds context only for AFClaude sessions, never blocks): in `~/.claude/settings.json`
   ```json
   {"hooks": {"UserPromptSubmit": [{"hooks": [{"type": "command", "command": "python3 <repo>/hooks/delegation_reminder.py", "timeout": 5}]}]}}
   ```
   (merge it into existing `hooks`; user level because it must also reach AFClaude sessions working in other directories; `AFCLAUDE_DIRS` overrides which directories count).
3. **Folder trust** (`hasTrustDialogAccepted` in `~/.claude.json`): run `./trust_dirs.sh` yourself (the repo, `probe/`, `data/` and the project folders; only inside `KA_TRUST_ROOT`). `ka_resume.sh` also marks a launch's cwd trusted. The live test needs `data/` trusted already.
4. **Guard hooks** (the owner's own `PreToolUse` hooks in the working root's `.claude/settings.json`) are not AFClaude's; AFClaude only relies on them honouring `CLAUDE_GUARD_DISABLE=1`.

`git config core.hooksPath .githooks` (the public-repo guard, below) is a git setting, not a Claude permission, but belongs to the same install checklist.

## Public repo guard

This repo is meant to be public, so nothing personal or host-secret may be committed. `tools/check_public.py` backs two hooks in `.githooks/`; enable them once per clone with `git config core.hooksPath .githooks`.

- `pre-commit` scans the staged change (added lines and paths) and then runs the type-checking gate (`mypy --strict` with `mypy.ini`, the `.venv`'s pinned mypy; a worktree uses the main checkout's `.venv`; no mypy = no commit), `pre-push` scans the full tree of every pushed commit plus the author, committer and message of new commits.
- Blocked: local-only and runtime paths (`BACKLOG.md`, `ALERTS.md`, `OPEN_QUESTIONS.md`, `data/`, `run/`, `probe/`, logs, `*.db`, state files), secrets (`docker/secrets/`, `.env`, `*.key`, `*.pem`, ssh keys), private key headers, common token formats (GitHub, `sk-`, Slack, AWS, Google), long high-entropy hex/base64 strings, and public IPv4 addresses (private and documentation ranges pass).
- The owner's identity is blocked without being written down: the e-mail only as a SHA-256 hash, and the account/org UUIDs, e-mail and names are read from `~/.claude.json` and the global git identity on each run. Extra local terms (domains, host names) go in `~/.config/afclaude/public_denylist.txt` (or `$AFCLAUDE_PUBLIC_DENYLIST`), which is not in the repo.
- A generic secret/IP false positive can be exempted with `public-check: allow` on that line. Don't use `--no-verify`.
- `python3 tools/check_public.py --tree HEAD` audits the whole tree; `python3 -m unittest test_check_public` tests the guard.
- Local only, read from disk: `BACKLOG.md` (the owner's future projects) and `OPEN_QUESTIONS.md` (questions for the owner; the quickview reads it). The alerts are in the DB (`tasks.py doc show alerts`); a legacy `ALERTS.md` stays local. `GOALS.md`, `PROGRESS.md` and `EXCEPTIONS.md` are the public build log and must stay free of personal and host-secret details.
- The history was squashed into a single initial commit before publishing (29.09.2026).

## Key findings (details in PROGRESS.md)

- `claude -p --no-session-persistence /usage` gives fresh session/week usage without a model call. The `~/.claude.json` cache alone can be days stale.
- The limit notice is a synthetic assistant entry (`error: "rate_limit"`). Metadata lines follow it, so check the last user/assistant entry, not the last line.
- `--bg` sessions are forked from the `claude daemon`: they inherit the **daemon's** env, and they are retired after 60 min idle. That's why AFClaude uses tmux instead.
- A non-bg `claude --resume <uuid>` (flags allowed) continues in place and reconnects Remote Control to the same RC session. It only forks if another live process holds the session.
- `--allowedTools` and `--tools` are variadic and swallow a positional prompt. Use `--flag=value` or stdin.
- Taking over a `claude rc` server's per-thread child and resuming does NOT move the thread: the original stays usable in the app and a second RC thread with the same uuid appears (two writers on one transcript). `preflight()` refuses such holders; plain interactive holders are safe to take over.
- Never dry-run with a faked clock on the real date: `handle_fire` stores a dry-run marker under the real window-start key and blocks that night's fire.
