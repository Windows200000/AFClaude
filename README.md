# AFClaude

> **⚠️ AI-generated.** All code and docs in this repository were written by Claude (Anthropic's Claude Code, model Claude Opus 5.5), running mostly unattended ("AFK") on the owner's server. A human set the goals and the rules and reviews the results, but did not write this code. Treat it as a prototype.

AFClaude keeps long-running Claude Code sessions going while nobody is at the keyboard. When a session hits its usage limit, AFClaude waits for the reset. Then, inside a nightly window and only if the weekly budget allows, it continues that same session. It is the first building block of a planned cross-session task system, in which every project is run by one Claude session, its *task-manager* ("manager" is reserved for a user role, see `docs/dashboard_design.md` §2).

## Rules

- **The core AFClaude session always runs on Opus 5.5 (`claude-opus-5-5`) with `--effort high`.** Subagents it spawns may use other models (e.g. Haiku for cheap classification). `keepalive.py` and `ka_resume.sh` default to exactly that.
- Permission modes for unattended runs (nothing may hang waiting for a human): main sessions `--permission-mode auto`, plus narrow per-launch allow rules (`ka_resume.sh`, `claude agents`) that are checked before the classifier. Haiku and other models without auto mode use `dontAsk`; so do all `claude -p` helper calls.
- Sessions launched by AFClaude get the guard-hook bypass (`CLAUDE_GUARD_DISABLE=1`) so they never hang unattended. They are told to read the guard hooks and respect them anyway.

## AFClaude container (docker/)

The container runs AFClaude's schedule and code, while everything that touches Claude sessions still runs on the host, through a strict SSH bridge.

- **Image** (`docker/Dockerfile`, `python:3.12-slim`): python3, supercronic (non-root cron), openssh-client, tini, procps, the MCP SDK, plus git/tmux for the unit tests only. It runs as UID/GID 1000 with `HOME=/home/opc`. The code is baked in at the host repo's own path, owned by root, so host-facing paths (cwd, PROGRESS.md in messages) stay the same.
- **Schedule**: `docker/crontab` mirrors the host's AFClaude crontab lines (sampler, window-start, watcher watchdog, usage review, quickview export, dispatcher). The entrypoint starts the watcher (`docker/start_watcher.sh`, the counterpart of `start_keepalive.sh`), which replaces the `@reboot` line. `at` is a shim (`docker/at_shim.py`) that spools the sampler's pre/post-reset jobs in `data/at_spool/`, run by a per-minute cron line. `AFCLAUDE_SCHEDULER=on|off` (default off: the container only idles).
- **Mounts** (no docker socket, no privileges, no ports, read-only root fs): the host repo read-only at `/host/repo`. PROGRESS/ALERTS/OPEN_QUESTIONS/BACKLOG/GOALS/EXCEPTIONS/README and PAUSED are symlinks to it, so reads are always fresh. `data/` is read-write. `~/.claude/projects` and `~/.claude/sessions` are read-only, plus the bridge key and the host's public ed25519 host key (for strict checking). `~/.claude.json` is **not** mounted: claude replaces that file, so a file bind mount would go stale. The usage cache comes via the bridge. Watcher state (`keepalive_state.json`, lock, log, STOP) is in `data/keepalive/`.
- **Bridge**: `host.py` runs `ssh opc@host.docker.internal` (host-gateway, `extra_hosts`) with the key from `install_host_bridge.sh`. The compose network is pinned inside `172.16.0.0/12`, which the key's `from=` requires. sshd runs `docker/host_exec.py` as a forced command, which accepts only its whitelist. Host behaviour without `AFCLAUDE_IN_CONTAINER` is unchanged.
- **Machine-specific values**: `docker/.env` (gitignored; template `docker/env.example`).
- **Run**: `docker compose -f docker/compose.yml up -d --build`. Unit tests inside: `docker exec -e AFCLAUDE_IN_CONTAINER= afclaude python3 -m unittest test_keepalive` (the tests use local stubs, so the bridge is switched off for them).
- **Dev override** (code from a checkout, read-only, no rebuild): `AFCLAUDE_DEV_SRC=/path/to/checkout docker compose -f docker/compose.yml -f docker/compose.dev.yml up -d`.
- **MCP server from the container**: `docker exec -i afclaude python3 /mnt/BlockVolume/Claude/work/AFClaude/mcp_server.py` is a drop-in stdio command (e.g. `claude mcp add --scope user afclaude -- docker exec -i afclaude python3 …/mcp_server.py`). The existing registration (host `.venv`) keeps working. Both use the same `data/afclaude.db`.
- **Stop / pause the container watcher**: `touch data/keepalive/STOP` (the next start removes it); `touch PAUSED` in the host repo keeps it stopped. `start_watcher.sh` never starts a second watcher while one runs on the host.

## Budget rule

Goal: use the whole weekly limit (about 100% at each weekly reset) with autonomous work, without ever getting in the user's way. Every point where a continue or a start could fire asks `keepalive.budget_eval()` (`budget_decision()` / `budget_headroom()` wrap it): the watcher, the window-start pass and its postponed recheck, the last-stretch pass, `--work-on`, `--decide`, the dispatcher's gate and the quickview. So they all show **the same number**, the "budget for this run" (weekly %, also ≈ session windows): the decision reason, `budget_headroom()`, `--decide`, the continue message and the quickview tile carry it. `data/afclaude.json` `"usage_model"` selects the model: `"pacing"` (default, `pacing.py`) or `"linear"` (the original rule). If `pacing.py` raises, the original linear rule decides (the reason says so), except inside the last stretch, which then holds: the linear rule cannot see the user.

### Pacing (`pacing.py`, default): the original linear rule, forecast-driven night gate

The original rule filled the week gradually along a straight line (continue while weekly % < 90 × elapsed / 7 d). Pacing keeps the gradual fill but decides with a forecast of the user's own use, in full session windows only (owner decision 04.10.2026):

```
threshold     = data/afclaude.json reserve_threshold: "auto" (default) = one session window left
                = 100 − full_session_cost, full_session_cost = 100 × ratio (now ≈ 15.4 → ≈ 84.6%);
                or a % override (50..99; a legacy week_target counts as the override)
At every decision (each session window of the night is re-checked):
    w             = weekly % now
    run_cost      = ratio × (100 − session %) of the live session window, else full_session_cost
    predicted_end = w + run_cost + forecast(now → weekly reset)
    RUN a full session window iff predicted_end ≤ threshold; budget for this run = run_cost
    otherwise no run (no partial runs); the next session-window start re-checks
    checked only at each session-window start of the night (23:00, 04:00; D-202), never in between
    without a forecast: the straight line, RUN iff w + run_cost ≤ threshold × elapsed at tonight's window end
The model has no margin: the threshold is the only spare.
CONTINUE also needs the user idle and the session < 85%.

Last stretch: the final min(ceil(sessions_left), 2) × 5 h before the reset,
    sessions_left = (100 − w) / (100 × ratio), ratio = limit_ratio.preferred_ratio() (0.2 if too little data):
    budget 100 − w, session cap 100%.   last_mile_hours: "auto" (this) or a number of hours (0 = off).
```

- **The forecast** is the user's typical weekly-% rise per hour of the week (Berlin weekday × hour) from the last 4 closed weekly cycles, with no margin. Intervals inside an autonomous AFClaude run (from a recorded keepalive / dispatcher / usage-review fire until the next prompt in an AFClaude session) are left out; usage the user drives in AFClaude sessions counts as the user's. Hours without data use the mean rate. Below 72 covered hours the straight line is used, and the reason says so.
- **Its accuracy is computed in code, not tuned by hand.** `pacing.forecast_backtest()` back-calculates the forecast's error from the usage data: at every past night session-window start, it fits the profile on the cycles closed before that point (what the gate would have used) and compares it with the user's real use until the reset (until now for the open week). `pacing.ratio_stats()` gives the session/weekly ratio's spread over the session windows (`limit_ratio.py`). `pacing.threshold_info()` combines them: ratio ± spread, full-session cost ± uncertainty, the model's bias / sd / rmse (n, how many points reach the reset), the predicted week end's uncertainty, the dynamic default and the active threshold with its source. `--decide`, `python3 pacing.py` and the quickview show it. Armed window-start decisions are also logged to `data/forecast_log.jsonl` and `pacing.forecast_errors()` scores them once the week has closed.
- **The run's own use doesn't flip the gate mid-session**: as AFClaude works, w rises and the rest of the session window shrinks together, so the predicted end stays the same. A daytime decision (`--now`, `--work-on`) uses the same gate.
- **User activity** (yield): only turns or prompts in non-AFClaude sessions (`activity.other`) and a weekly-% rise without any local turns (another device or claude.ai). The user's own input to AFClaude sessions does not count. Missing or stale (> 30 min) sampler data counts as active.
- **A HOLD for the user postpones**: recheck at last activity + `idle_min` (60 min), then fire if still allowed. The watcher re-evaluates a postponed stall then; a postponed session-window start is kept in `keepalive_deferred.json` and re-decided by the watcher under the same once-per-start key, only until the night's next session-window start (a run started later would end after the window end; D-202), else it is skipped to that start; the dispatcher decides again on its next pass. Unknown activity or usage: recheck after 15 min; session guard: at the session reset. This also applies in the last stretch (`last_mile_yield`, default true).
- **The last stretch** is continued once per session slot by the watcher (`last-mile-<reset>-s<k>`); the dispatcher's window gate and 85% session stop are lifted there (100%).

Optional overrides in `data/user_model.json` (local; top level or a `"pacing"` object): `idle_min`, `min_gap`, `session_cap`, `last_mile_yield` (the retired `forecast_margin` is ignored). `python3 pacing.py` prints the current decision and `threshold_info()`; `python3 keepalive.py --decide` adds the last-stretch period and postponed window starts. `tools/budget_backtest.py --reset <ISO> --user-until <ISO> [--threshold auto|<pct>]` replays one weekly cycle of `data/samples.jsonl` for the original linear rule, the retired reserve model (`usage_model.py`, kept only for this comparison) and pacing with the straight line and with the forecast (end-of-week %, min/p10 user headroom, blocked user demand, AF-caused session hits, nights with work, forecast error).

### Linear rule (`"usage_model": "linear"`, and the fallback)

1. in the last stretch (`last_mile_hours`, "auto" as above) → continue up to 100%
2. projected end-of-week usage < 90% → continue (linear extrapolation over the elapsed week, elapsed floored at 24 h)
3. otherwise, continue only if the weekly reset is ≤ 11:00 Berlin after the current window
4. otherwise, hold

## Task-manager mode

Every continue/start message ends with `prompts/manager.md`: the controlling Opus session acts as the project's task-manager and hands concrete work to subagents. That keeps its context for decisions and state, so it can hold more of the project at once. All AFClaude-run projects use the same file. It's based on the Claude Code docs: best-practices "Use subagents for investigation" ("Since context is your fundamental constraint, use subagents to keep research out of it…") and workflows "When to use a workflow" (Claude as the orchestrator that only receives final results).

## Public repo guard

This repo is meant to be public, so nothing personal or host-secret may be committed. `tools/check_public.py` backs two hooks in `.githooks/`; enable them once per clone with `git config core.hooksPath .githooks`.

- `pre-commit` scans the staged change (added lines and paths), `pre-push` scans the full tree of every pushed commit plus the author, committer and message of new commits.
- Blocked: local-only and runtime paths (`BACKLOG.md`, `ALERTS.md`, `OPEN_QUESTIONS.md`, `data/`, `run/`, `probe/`, logs, `*.db`, state files), secrets (`docker/secrets/`, `.env`, `*.key`, `*.pem`, ssh keys), private key headers, common token formats (GitHub, `sk-`, Slack, AWS, Google), long high-entropy hex/base64 strings, and public IPv4 addresses (private and documentation ranges pass).
- The owner's identity is blocked without being written down: the e-mail only as a SHA-256 hash, and the account/org UUIDs, e-mail and names are read from `~/.claude.json` and the global git identity on each run. Extra local terms (domains, host names) go in `~/.config/afclaude/public_denylist.txt` (or `$AFCLAUDE_PUBLIC_DENYLIST`), which is not in the repo.
- A generic secret/IP false positive can be exempted with `public-check: allow` on that line. Don't use `--no-verify`.
- `python3 tools/check_public.py --tree HEAD` audits the whole tree; `python3 -m unittest test_check_public` tests the guard.
- Local only, read from disk: `BACKLOG.md` (the owner's future projects), `OPEN_QUESTIONS.md` (questions for the owner; the quickview reads it) and `ALERTS.md`. `GOALS.md`, `PROGRESS.md` and `EXCEPTIONS.md` are the public build log and must stay free of personal and host-secret details.

## Key findings (details in PROGRESS.md)

- `claude -p --no-session-persistence /usage` gives fresh session/week usage without a model call. The `~/.claude.json` cache alone can be days stale.
- The limit notice is a synthetic assistant entry (`error: "rate_limit"`). Metadata lines follow it, so check the last user/assistant entry, not the last line.
- `--bg` sessions are forked from the `claude daemon`: they inherit the **daemon's** env, and they are retired after 60 min idle. That's why AFClaude uses tmux instead.
- A non-bg `claude --resume <uuid>` (flags allowed) continues in place and reconnects Remote Control to the same RC session. It only forks if another live process holds the session.
- `--allowedTools` and `--tools` are variadic and swallow a positional prompt. Use `--flag=value` or stdin.
- Taking over a `claude rc` server's per-thread child and resuming does NOT move the thread: the original stays usable in the app and a second RC thread with the same uuid appears (two writers on one transcript). `preflight()` refuses such holders; plain interactive holders are safe to take over.
- Never dry-run with a faked clock on the real date: `handle_fire` stores a dry-run marker under the real window-start key and blocks that night's fire.
