## 4. Architecture

Option A (D-071), with the language split of D-208/D-209: **AFClaude stays Python; the dashboard UI is TypeScript in the browser.** A small Python web app next to the DB (Starlette + uvicorn) serves the JSON API (§8) and the built frontend as static files; it keeps everything that decides or protects: login (OIDC + groups, password + 2FA, passkeys), sessions, roles, CSRF, the API and the single write path (`actions.py`). The TypeScript frontend only renders what the API returns and sends the user's writes back to it; it holds no authority (every check is repeated server-side) and no secrets. It is compiled to static files when the image is built (a JS build step in the build stage only, §10.1); **no Node in production**, no CDN.

```
browser (TS app: static files) ──https──> reverse proxy (Traefik / Coolify)
                      │  (no internet route until gates 8a–8c pass, D-157)
                      v
   afclaude-web ──────┐ actions.py ─> store.py ─> SQLite WAL (volume /data)
   (Starlette: JSON API + static files + auth)
   afclaude-mcp ──────┤      ^                         ^
   afclaude-runner ───┘      │ wake (unix socket in /data/run)
     ├ dispatcher tick, window-start tick, run-now
     ├ stall scan, sampler, usage review, build-log export, backups
     └ session executor ──ssh bridge──> host: tmux + Claude CLI sessions (D-164)
```

- **One image, three services** (D-163): `afclaude-web` (the dashboard's HTTP port), `afclaude-runner` (a resident daemon, §5.1), `afclaude-mcp` (the MCP server; its only port is the remote MCP transport, §4). All share the data volume. SQLite WAL across containers is fine on one kernel; never on a network filesystem, so all three run on one host.
- **Usage numbers** reach the dashboard through a `status_snapshot` row the runner writes each pass (usage %, resets, budget decision, `threshold_info()`, ratios). The web container imports no model code and never reads `~/.claude.json`, calls `/usage`, `claude`, tmux or the bridge. Pages show the snapshot's age.
- **Sessions stay on the host** (D-164): AFClaude itself (web, runner, MCP) is containerised; the Claude CLI sessions run in tmux on the host, started by the runner through the whitelisted SSH bridge (D-120, D-121), in AFClaude's own working root (§10.4). The dashboard validates the host setup (§10.5).
- **MCP transport:** the `afclaude-mcp` container. On the AFClaude host it is registered as a stdio command (`docker exec -i afclaude-mcp afclaude mcp`), which works today. Other machines reach it through a remote MCP transport (D-198: streamable HTTP on an internal port of `afclaude-mcp`, routed by the reverse proxy at `<AFCLAUDE_PUBLIC_URL>/mcp` with TLS, so it follows the exposure stages of §9.2: tunnel or VPN only until gate 8d). Every interactive connection authenticates with its machine's token (§9.7).
- **Frontend stack (D-208/D-209; the choice of library is a *proposal*).** The UI is phone first, server-authoritative (every write returns the new state, the page re-renders from it; no client-side store or cache of truth) and about 15 views of cards, lists and forms. Options checked:
  - **Plain TypeScript + a small own router:** no runtime dependency at all, but every view would update the DOM by hand; that drifts towards `innerHTML` templates (the XSS sink we want to avoid) or verbose element code, and strict typing then can't check the markup.
  - **Lit (web components):** small and standard-based, but its templates are tagged strings that `tsc` doesn't type-check without an extra analyser, and shadow DOM fights the one global strict-grid stylesheet (D-074).
  - **Preact (chosen):** about 4 KB, no dependencies of its own, mature (since 2015, React's API); TSX templates are fully checked by `tsc --strict`, and text is escaped by default, so the only raw-HTML sink is one audited component (§9.8). React, Vue, Svelte and Solid were ruled out by size or by the compiler and plugin trees their builds pull in. The earlier server-rendered design (Jinja2 + htmx, no JS build) is superseded by D-208.
  - **Tooling:** `typescript` (`tsc --noEmit`, `strict: true`) for type checking, `esbuild` (one package plus its platform binary, no other dependencies, works with `--ignore-scripts`) for bundling, Node's built-in `node:test` for unit tests, `preact-render-to-string` for component tests. Routing is a small own history router over a typed route table (the views are a fixed list), no router package. **No charts** (D-297: the design's two charts are dropped, the two usage lines are enough): no chart library, so the whole npm tree is about four packages: runtime `preact`; build/test `typescript`, `esbuild`, `preact-render-to-string`. Every added package is a design change listed here, for supply-chain reasons (§9.8).
- **API types (D-209):** the request and response shapes are declared once, in Python (typed, checked by `mypy --strict`); a repo script generates the JSON Schema of `/api/v1` and the TypeScript types from it (no codegen package). A test fails when the committed generated files differ from a fresh run, and the API contract tests validate every response against the schema (§12), so the frontend can't drift from the backend unnoticed. No `any` in the API types or the API client.
- Code layout: `dashboard/` (Starlette app, API routes, the API schema, static-file serving), `dashboard/web/` (the TS frontend: `package.json`, `package-lock.json`, `tsconfig.json`, `src/`, tests; built into the image, the build output is not committed), `actions.py`, `schedule.py`, `prompts.py`, `runner.py` (daemon), `auth/` (sessions, password, TOTP, WebAuthn, OIDC), `backup.py`, `docker/`. The flat modules stay.
- **Strict type checking (D-209), mainly for security.** `mypy --strict` is mandatory, enforced by the test suite and the pre-commit hook, for the security-relevant Python code: auth, sessions, roles, the API layer, the write path (`actions.py`, `store.py`), the MCP server, the host bridge (`docker/host_exec.py`) and backup/export/restore. The list of strict modules lives in one config file and only grows; other modules adopt it gradually (modules outside the list don't block the check). The TS frontend compiles with `strict: true`. Phasing: §13.
