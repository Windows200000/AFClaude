## 3. Main flows (phone first)

One column, large tap targets, no hover-only controls, no drag-and-drop as the only way to reorder, every page useful on its first screen. Top bar: automation state (running / paused, toggle), a small status dot for the runner (D-230, §3.1: green = running, the usual status colours otherwise, tap/hover for the detail text — no separate status tile), tonight's window ("23:00–09:00, 2 × 5 h"), the projected end of week, inbox badge. Every view is filtered by the viewer's grants.

- **F1 Inbox (home).** Inbox: only real questions (D-083): open questions (`kind='question'`) and blocked tasks (from agents only once their task-manager forwarded them, §7.9); decision proposals waiting for confirmation. A project's questions go to the owners and that project's managers and editors, **each question with its own answer input** (D-300: free text, plus the lettered options as quick-select buttons feeding the same box when the question states options — never one combined reply for several questions); the project's viewers see the same cards read-only, without a box (D-196). Never stalls, never untitled sessions. Answering removes the card at once (the server returns the new inbox). Empty inbox = one line. Below it, the overview (D-230, §3.1): the session/week usage bars with their reset time (D-074's bars, kept); "Holding until" / the next run (D-201) as today|tomorrow|weekday + hour, minutes as a small superscript only when they aren't :00 (D-230); the phase strip (D-084/D-085) of the project AFClaude is currently working, then the lineup — the ordered list of what runs next once that phase/task/project is done, from the dispatcher's project/stage order (D-064) and each item's stage ETA (D-213), numbers only, no narrative line. Below that, one input block per project the user is editor, manager or owner of, with that project's important tasks shown and minor ones collapsed (§3.1), and the project's two input boxes, never merged (§3.1): an instruction and a question (F14).
- **F14 Message the task-manager (D-178, D-186), the question box of F1's two per-project inputs (§3.1).** A general box for anything that isn't an answer to an open question, mainly questions to a project's task-manager or new goals; a minimal embedded chat. The box addresses one project's task-manager (a project picker over the projects the user is editor, manager or owner of). It starts as one text box; after sending, it shows the message and, once it arrives, the task-manager's one reply. It grows into a chat (the thread with a new box under it) only when the user sends a follow-up. After `ui_chat_reset_hours` (default 5 h) without a new message in the thread, the thread is closed and the page shows an empty box again (closed threads stay in the DB, reachable from "earlier messages"). Mechanics: each message is a row in `chat_messages` (§7.2); sending queues a `task_manager_message` request. **Who wakes it (D-186):** a message from an owner or from a manager of that project wakes the runner, which delivers it to the task-manager immediately, like run-now (D-153, §5.4: no window or budget check, works while paused, preflight applies): a running task-manager gets a short notice at its next idle point, an idle one is resumed with it. A message from an editor waits for the task-manager's next regular run (its continue prompt carries it; a task-manager that is running anyway gets it at its next idle point). The task-manager reads the thread and replies through MCP (`afclaude_messages`, `afclaude_reply`; the reply is a task-manager write, not an agent write); goals it accepts it records through its normal tools (tasks, docs) and says so in the reply. While waiting, the card shows the request state (queued → delivered → answered). *Interim, built on the temp dashboard (D-241):* the quickview has the box (`inbox.py`, `inbox_worker.py`, `inbox_api.py`; table `inbox_messages`, setting `ui_chat_reset_hours`); Haiku sorts each owner message first: "now" wakes the task-manager as above (through the keep-alive's session lock, preflight and owner-typing checks), "note" is not delivered but listed verbatim in its next continue or post-compaction message, so a note never costs a cold-cache re-read (D-237/D-238); the reply is `tasks.py inbox reply <id>`. A "now" message the session can't take yet (the owner holds it or is typing, a compaction, a usage limit) is held and retried while the hold lasts, at most until the next session-window start (D-244; the box shows "held until <window start>"): that start's message takes it along, marked as needing an answer (its `[AFClaude inbox #id]` marker and `tasks.py inbox reply`); not out by then (the start skipped, held, failed or postponed) is an error. Every inbox failure (triage, delivery, the marker missing from the transcript, a missed hold deadline, a DB failure) is an error on the message, an alert and an automation pause (D-244, `failstop.py`) of the project the message was for (its own pause, table `project_pauses`; the owner clears it with `tasks.py automation resume --project NAME`).
- **F2 Stalled sessions.** Only sessions whose last entry is a limit notice (D-041), newest first, own AFClaude sessions hidden by default. Card: title (or cwd + first prompt), project, stall kind, reset time, the effective decision and its source. Buttons: Continue, Ignore, "Always…" (session rule or project rule, preselecting the most specific cwd), and **Run now** (§5.4). Undecided stalls never expire; decided ones move to a "decided" filter. RC-server threads show "continue it from the app" (§10.8).
- **F3 Queue and projects.** Ranked projects with their stages and a priority chip (tap cycles high → medium → low, D-064). Up/down buttons, "move to position…", optional drag on desktop. Per-project menu: whole project to medium/low, **edit name and description** (both plain fields, editable any time, D-301: the name is sent to the task-manager with every continue, so renaming takes effect at once; the description is the project's one-off kickstart, sent in full only at the project's first start — editing it afterwards doesn't resend the kickstart, it only tells the task-manager once that the description changed, so it can decide whether to act on the new text), its task-manager session, **Work on now** (owners and the project's managers, D-036, §5.4), members (grants). A second tab shows the flat execution order and why an item is skipped. Each project's task list shows only its important tasks (blocked/needs input, in progress, or the project's top stage priority); the rest collapse under one "+N more" row (D-230, §3.1).
- **F4 Window planner.** Seven rows Mon..Sun with each night's window or "off"; linked days share a colour (D-034, §6). Editor: change all linked / only this day / whole week; preview over the next 7 nights incl. DST nights and the weekly-reset marker; the measured ratios (`limit_ratio.py`: weekly % per session window, windows per week and left, AFClaude vs user share, each with "insufficient data" when honest). Save applies at once (the runner is woken).
- **F5 Status.** Runner health (last tick per job), the latest budget decisions with their reason, run log, the next usage review (a compact duration, D-230, §3.1: `3w`/`3d`/`2h`), review results split into universal and user-specific, and the reserve-threshold numbers (§3.1).
- **F6 Driven sessions.** Every session AFClaude started or continued: readable tmux name (§5.3), kind, project, state, RC link when known, the latest hand-off.
- **F7 Decisions.** Per project (and install-wide): the current decisions (D-104, D-158), keyword filter, proposals with "confirm / reject / edit" (for those who may confirm, §7.6), "propose a change".
- **F8 Prompts.** Every prompt with its placeholders and the session kinds that use it; default, the owner's system-wide override (D-193; there are no per-project prompt overrides), the effective bundle per session kind rendered with a chosen project's variable values (D-197), diffs against the default and the "default changed since your edit" flag (`base_outdated`; saving the same text again re-confirms it). Edit, validate (the placeholders must be exactly the prompt's system and project variables; the body is test-rendered in the prompt and every bundle that sends it), save, reset; the project's variable values are edited beside it. Built so far: `prompts.py` and the read-only MCP `afclaude_prompts`; the page itself is 7b.
- **F9 Docs.** Per project: goals, progress, alerts, exceptions, reviews, the phase strip (D-084, D-085); the agent-proposal queue and the run summaries with their review state (§7.9), where owners and the project's managers and editors can decide proposals (D-190).
- **F10 Settings.** Grouped sections (§7.4), incl. auth and session lifetimes (§9.5), users and grants (incl. machine users: rename, revoke and re-issue their tokens, §9.7), backup and the full export with its reinstate guide (§11).
- **F11 Account.** My logins: passkeys (with the hardware / synced badge), TOTP, recovery codes, OIDC links, active sessions and remembered devices with "sign out", display time zone.
- **F12 Audit.** The last N writes with actor, via, before/after summary; undo where the action supports it (D-075).
- **F13 Host.** The host validation (D-164, §10.5): tmux, Claude Code, login, bridge, working root, permissions, MCP, each ok / warn / fail with a fix hint; "run all checks" and the end-to-end session test.
- **Add task** (secondary): title, description, project, priority. This is F1's instruction box per project (D-230): free text becomes a task/goal for that project's task-manager, picked up at its next run, or run-now by role (D-153, D-184, §3.1).

First login: a popup offers the browser's time zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`). For the first owner it sets the global `window_tz` (Europe/Berlin until then, D-173); for everyone it sets their display time zone. Both stay adjustable (D-148).

### 3.1 UX rules (owner, kept)
- **Visual design (D-074):** purple main accent; vibrant colours that directly represent status (done / in progress / pending / blocked / alert), used the same everywhere; rigid but sleek: a strict grid, clear boxes and chips, compact, no decorative fluff.
- **Settings UX (D-075):** only the most important settings on the main views (pause, tonight's window, `last_mile_hours`, the budget mode); everything else on the Settings page in sections. Every setting has a default, its own reset, a short explanation of what it does and what it can affect (e.g. "can make AFClaude run during your daytime"). "Reset this section" and "Reset all" show a warning listing what changes, plus one-tap UNDO from the audit log. The registry (§7.4) is the single source; the UI renders from it.
- **Simple numbers (D-230):** nothing beyond the kept session/week usage bars (D-074) is a slider or a gauge — everything else is a number. "Holding until" / the next run (D-201) shows as `today 23:00` / `tomorrow 04:00` / `Tue 23:00` (a weekday name beyond tomorrow), never a countdown; the hour shows alone when the minutes are :00, otherwise the minutes follow as a small superscript (`23³⁰`). Durations shown anywhere (the next usage review, stage ETAs D-213, reset countdowns) are compact units with no space: `3w`, `3d`, `2h`, `<1h`, `~` only when estimated (`~3d`). The runner/watcher state is one small dot in the top bar (green = running, the usual status colours otherwise), tap/hover for the detail text — no separate status tile.
- **Tooltips (D-230):** every non-obvious label, number or control gets a custom tooltip (never the browser's native title attribute): it appears instantly on hover, with a short, subtle show animation (~120 ms fade/scale) that `prefers-reduced-motion` skips; on touch devices the first tap shows it, a second tap (or a tap elsewhere) dismisses or acts. The explanation lives in the tooltip; the label stays a noun or a number.
- **No filler text (D-230):** labels are nouns or numbers; no taglines and no sentences that restate what a section already shows (e.g. "easy overview dashboard for X", "future projects in a line-up based on what comes next"). Any explanation belongs in that element's tooltip, never in page text. Gate 8a reviews every page against this rule (§13).
- **Task lists: important vs. collapsed (D-230):** a task is **important** when it is blocked or needs input, in progress, or at its project's top stage priority; every other open task collapses under one "+N more" row, expandable. Applies wherever a project's tasks are listed (F1, F3, F9).
- **The lineup (D-230):** under the current project's phase strip (D-084/D-085), a short ordered list of what AFClaude works on next once that phase/task/project is done — the dispatcher's project/stage order (D-064) with each item's stage ETA (D-213). Shown on F1 and F9; position, project/stage name and ETA only, no narrative text.
- **Two inputs per project (D-230):** every project's input on F1 is two separate boxes, never merged: an **instruction** (becomes a task/goal for that project's task-manager, picked up at its next run, or run-now by role, D-153/D-184) and a **question** (F14/D-178's message box: an immediate answer, wakes the task-manager for owners/managers, waits for the next run for editors, D-186).
- **Reserve threshold UI (D-141):** next to `reserve_threshold` ("auto" or a %) show, all computed in code by `pacing.threshold_info()`: the session→weekly ratio ± spread (n); the weekly cost of one full session window ± uncertainty and the dynamic default (100 − that cost); the model's back-calculated inaccuracy (`forecast_backtest()`: bias, sd, rmse, n, points reaching the reset, preliminary/ok); the predicted week end's uncertainty and its slack to the threshold; the active threshold and its source. One line explains the rule: a night runs a FULL session window only if the week is then predicted to end at or below the threshold; the model has no margin, the threshold is the only spare.
- **Stage ETAs (D-213):** F3 (each project's stages) and F9 (the phase strip) show every open stage's and phase's cumulative ETA as a compact duration (`~3d`, `<1d`, `?` when unknown, D-230, §3.1) from `stage_eta.py`, with the assumptions one tap away: the capacity in session windows/day (what the night gate and the last stretch allow with the usage prediction, next to the owner's formula (100 − the user's forecast week) / the weekly % of one session window), the ratio and threshold, and how many stages use their own `estimated_sessions` vs the history default vs the fallback. `estimated_sessions` is a task field (editable in F3 by editors and the task-manager, through `task.edit`, D-185); the daily prediction log moves from `data/stage_eta_log.jsonl` into a DB table with the rest of the telemetry (D-161), and the review's score shows in F5 next to the usage review.
