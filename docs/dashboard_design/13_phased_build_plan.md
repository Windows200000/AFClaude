## 13. Phased build plan

Each phase is one subagent in a worktree with a clear definition of done (tests green, `check_public` clean). Runner phases keep every existing suite green and are deployed autonomously within the gates (D-106). No dashboard deploy before 8b, no internet route before 8d, nothing from the dashboard reaches Claude before 8d (D-072, D-157).

1. **Config + v4 schema + `actions.py`.** Done (01.10.).
2. **Backend foundation**
   - **2a Settings in the DB (D-146):** every tunable into `SETTINGS` (afclaude.json, dispatcher.json), one-time import, runners and pacing read the DB, schema guard (A1), the DB error path and escalation (§7.8, D-171). **Type-checking gate (D-209):** `mypy --strict` for `actions.py`, `store.py` and the MCP server first, enforced in the tests and the pre-commit hook (pinned mypy, the strict module list in one config file); each later phase adds the security-relevant modules it creates or touches (5a auth, sessions, roles; 5b `docker/host_exec.py` and the remote MCP transport; 5c/5d backup, export, restore; 6a the API layer), so the full list of §4 is strict by 8a.
   - **2b `schedule.py` (D-148):** the only window code, pacing included; DST tests; `window_tz` plumbing.
   - **2c Telemetry into the DB (D-161):** usage tables + importers; sampler, `limit_ratio`, `pacing`, `usage_review`, `usage_report` read/write the DB; `account_id`. *Built (first step):* the tables (append-only rows immutable by trigger, written through registered `actions.py` appenders, each row the file's line with ts/actor/via/`account_id`/`stale`; derived records with a version), `python3 store.py import-telemetry` (idempotent, checks every row arrived, marks the kind imported, never touches a file), dual-write in every producer, and the readers on the DB once a kind is imported (the files as fallback). Left (the file retirement is built, see below; `usage_reviews` came with 2d part 2): a samples retention setting.
   - **2d Runner state + docs into the DB (D-161, D-181):** state files, own sessions, scheduled jobs, logs → DB; `docs`/`doc_entries`, with the AFClaude build-log export (§7.7) as the only file output. *Built (part 1, runner state):* `runner_state` (one row per top-level key, or per entry of the maps the runners update entry by entry: keepalive handled/fires/limit hits, dispatcher sessions/handled/…, sampler offsets/sessions; trigger-bumped version; deleted only where the runner deletes), `scheduled_jobs` (the at-shim's spool, started jobs marked, never deleted), `app_log` (append-only, immutable by trigger), own sessions into `driven_sessions` (kind `own`); written through `actions.py` (`state_save` in one transaction per save with one audit row naming the changed paths, actor `runner:<component>`; `app_log_append`/`app_log_sync`; `job_put`/`job_started`, `own_session_add`, audited). `python3 store.py import-state` (idempotent, never touches a file, checks row by row, marks each component imported). Dual-write in keepalive, dispatcher, sampler, usage review, the at-shim and the keepalive/dispatcher/sampler log lines; the state readers (incl. pacing, usage_model, run_metrics, the quickview) read the DB once imported and while the file carries the mark of a DB save, else the file. Concurrent savers merge per entry in the DB (the file stays last-writer-wins). Left: retiring the files (the DB as the only copy, the full §7.8 path), the log readers on `app_log` and a log retention setting, the redirect-only logs (host_exec, watchdog, at_shim, sampler tracebacks) synced only by re-running the import, `status_snapshot`/`host_checks`. *Built (part 2, docs):* `docs`/`doc_entries` (§7.2, §7.7: logs append, whole documents versioned, one append-only entries table, a sync mark per doc), `doc.append`/`doc.set`/`doc.sync` in `actions.py`, `project_docs.py` (`import`: PROGRESS, GOALS, EXCEPTIONS, ALERTS, `data/reviews/*.md`, idempotent and checked byte for byte; `export`: the public build log from the DB, byte-identical, `check_public`-checked, the only file output, D-181), `tasks.py doc …`, MCP `afclaude_doc`; dual-write with the files. *Built (part 2, the switch, §7.7):* the scheduled import (every 10 min, merging hand edits with the runners' notes: `docs.file_text` + `actions.merge3`), `notify.py`/`keepalive.py` notes through `doc.append`, `ALERTS.md` and the review files no longer written (reviews: `tasks.py doc set review:<date>`), the quickview reading the docs from the DB, `manager_afclaude.md` and the review prompts on `tasks.py doc …` + `doc export` before commits, `usage_reviews` (2c) as the review docs' structured part (one record per launch). Left: role-restricted doc writes (5a).
   - **2c/2d file retirement (D-161), built:** the DB is the only copy of every telemetry kind, the runner state (keepalive incl. deferred / fill-up / usage refresh (the hand-off saves component `keepalive.handoff` is retired since D-233: the save prompt is part of the start), dispatcher, sampler, usage review), own sessions and scheduled jobs: the producers write the DB only (`telemetry.record` / `write_records`, `runner_state.save`, `job_add`), a DB failure takes the full §7.8 path (`store.retrying`, then the failed rows / changed state rows / job into `data/ALERTS.fallback.md` with `report_db_error(runner=True)`: the same action failing again alerts once per episode unless db_gate's pause episode is open; `store.db_gate` pauses the runners); the readers, the writers' own "already recorded?" checks, `track_cycle`, `usage_model.load_params`, the settings import's user-model source, the own-session lists of `stalled`/the sampler/`actions` and the quickview's latest sample read the DB (an unreadable DB: no rows / an empty state, never a file). The usage review writes the user model with `python3 telemetry.py user-model set` (the audited action `user_model.set`); `telemetry.py rows <kind>` prints a kind. The at-shim keeps jobs in `scheduled_jobs` (claimed by marking them started; a legacy spool file the DB doesn't know is adopted, the spool dir is never written). Legacy files stay frozen in `data/` (safe to archive): a kind/component never imported is read from its file until its first DB write imports it; the importers skip what is imported (`import-telemetry --catch-up` re-imports the append-only kinds). Supersedes "retiring the files" in 2d's Left; the logs stay files (dual-written into `app_log`).
3. **Runners**
   - **3a Resident runner (§5.1):** daemon with the job table, stall-scan tick, status snapshot, wake socket, all runner writes via `actions.py` (D-154), `run_log`/`driven_sessions` filled.
   - **3b Task-manager unification + run-now (D-147, D-153, D-036, D-189):** the AFClaude task-manager as an ordinary project's task-manager, chosen algorithmically at each start by project rank (D-205; one per project, no global one), keep-alive continuation retired, readable tmux names, `continue_now`/`work_on_now`/`review_now` skipping window and budget (owners and managers only). Implementation plan: `docs/phase3b_plan.md`.
   - **3c Compaction hand-offs (D-144, D-155, D-191, D-218):** `handoffs` per driven session, the trigger (D-238: at a run end or ~50 min idle while the cache is warm, above the computed break-even), the save prompt directly before the `/compact` (D-233), MCP tool, `/compact` + resume prompt.
4. **Content stores**
   - **4a `prompts.py` (D-111, D-152):** project scope (migrate step), bundles per session kind, every sender uses it.
   - **4b Questions, decisions and task-manager messages in the DB (D-151, D-158, D-176, D-178, D-181):** `decisions` + links + FTS, proposals as questions, MCP tools (relevance-only summaries, expand before acting), seeding, `OPEN_QUESTIONS.md`/`DECISIONS.md` retired (no export, D-181), prompts and CLAUDE.md rules switched to the DB; `chat_threads`/`chat_messages`, the `task_manager_message` request (waking the task-manager for owners and managers, waiting for editors, D-186), MCP `afclaude_messages`/`afclaude_reply` and the task-manager prompt's instructions for them.
5. **Users, packaging, backup**
   - **5a Users, roles, task-manager and agent roles (D-149, D-160, D-182–D-190, D-195, D-196):** users/grants schema (owner, manager, editor, viewer), actor = user, machine users (`users.kind`, `machine_tokens`, `machine_registrations`, `afclaude machine register`, token check on the stdio MCP connection, audit actor `machine:<id>`, no access until granted), question visibility (owners, managers, editors answer; viewers read-only), the role matrix in `actions.py`, task-manager/agent detection (incl. whether subagents can be told apart), `agent_proposals`/`agent_runs`, run summaries, MCP `afclaude_proposals`/`afclaude_review`, immediate delivery of proposals to the task-manager (D-188), the task-manager's own review of finished branches before merging (D-185), the task-manager and agent prompts' instructions, alerts on violations. Implementation plan: `docs/phase5a_plan.md`.
   - **5b Containers + host checks (D-163, D-164):** one image, web/runner/mcp services, compose for docker and Coolify, minimal env, master key, MCP in a container, the remote MCP transport with machine-token auth (§4, §9.7), cut-over from the current container and host crontab; sessions stay on the host via the bridge; the host checks (§10.5) as a runner job + CLI, with the bridge whitelist extension. Implementation plan: `docs/phase5b_plan.md`.
   - **5c DB backup / restore / move (D-161, D-175, D-180, D-187):** bundle, restore, `restore_starts_paused`, move fence, CI round trip; the WAL archive with Litestream (`db_wal_retention_days`, rollback to a moment, archive in the bundle, disk use measured); `AFCLAUDE_DATA` required with no default, set at setup together with the optional restore (the working root likewise, 5d).
   - **5d Claude data export + working root (D-165, D-187):** first-startup working root (no default, chosen at setup and at restore) and config dir (CLI; the UI follows in 6a), verify `CLAUDE_CONFIG_DIR` on the host (RC, `/usage`, `claude agents`, login), the `claude/` export part, whitelisted restore command, path map, the generated reinstate guide, post-restore validation. Implementation plan: `docs/phase5d_plan.md`.
   - **5e One-off migration of this installation (§11.5, D-180, D-187):** the end-to-end test of backup → export → restore, covering both folders: the normal backup and export with the AFClaude selection filter out of the shared root and config dir, restored at setup into a new data directory and a new working root on this host (both chosen at that setup, no defaults), with the dedicated config dir; every gap fixed in the export and the run repeated from scratch, until validation, the end-to-end session and a real task-manager continue pass.
6. **Dashboard**
   - **6a Skeleton + local auth:** Starlette JSON API (`/api/v1`, error shape, the typed schema and the generator for `schema.json` + TS types, contract tests) serving the built frontend; **TS frontend scaffold** (D-208/D-209): `dashboard/web/` with `package.json` + lockfile (the §4 packages only), `tsconfig.json` `strict: true`, esbuild build, `node:test` + component tests, the typed API client (CSRF header, idempotency keys, error codes), the own router, the app shell, layout + top bar (D-074); the multi-stage Dockerfile (§10.1) with typecheck, tests and `npm audit` in the build stage; sessions and lifetimes (§9.5), password + TOTP + recovery codes, setup/first registration and the first-startup wizard (§10.4) as TS views over the auth API, CSRF for the SPA, headers and CSP (§9.8), route-table and matrix tests, `health`; the API layer joins the `mypy --strict` list. Implementation plan: `docs/phase6a_plan.md` (W1 API skeleton and W2 typed schema + TS codegen built). **Owner preview (D-211, §10.9) becomes possible here** for the first time: the preview build + mock client, deployed to its own `/private` path; redeployed after this step and after every UI step through 7b, each with a non-blocking review item in "needs your input".
   - **6b Passkeys + OIDC (D-150, D-159):** python-fido2 with MDS3, BE rules and warnings; the WebAuthn begin/finish ceremonies from the TS client (§8); Authlib OIDC with the group map as a backend redirect flow (no provider token in the browser); step-up re-auth (the client's re-auth dialog and retry on `step_up_required`); F11. Preview redeployed (D-211).
   - **6c Read views:** F1–F9, F12, F13 and the threshold panel as TS views over typed read endpoints (each with its schema entry and contract test); no charts (D-297: F4/F5 show the measured ratios and usage as numbers only), server-sanitised markdown through `SanitizedHtml` only, request-state polling; RC URL source verified. Preview redeployed (D-211).
7. **Writes**
   - **7a Work writes:** answers, the task-manager message box (F14, D-178, D-186), tasks, projects, priorities, moves, decisions and proposals; each write a typed endpoint with its contract test, sent by the API client with idempotency key and `version`; 409 handling in the UI (show the current row, edit onto it or drop). Preview redeployed (D-211).
   - **7b Control writes:** stalls and rules, window editor, prompt editor, pause, run-now with live feedback (request polling), Settings page rendered from the registry's schema with reset/undo (D-075), users/grants incl. machine users (registration code, rename, revoke, re-issue; the token shown once and never stored in the browser), backup and export UI (downloads as plain authenticated GETs, no tokens in URLs), confirm + step-up for high-impact writes; each write typed and contract-tested. Preview redeployed (D-211); from 8a on, further review happens on the putup deployment itself. Implementation plan for 7a and 7b: `docs/phase7_plan.md`.
8. **Deploy gates, strictly in this order (D-072, D-145, D-157):**
   - **8a Thorough review (Opus 5.5, ultracode/max effort).** The whole dashboard and its integration: `actions.py`, `schedule.py`, `prompts.py`, the runner, auth (OIDC + groups, password + 2FA, passkeys + MDS), backup, export and restore, the host checks, containers. It also checks that **the docs and every owner decision agree with the actual code**, not only with comments and explainer files; every discrepancy goes to the owner to decide, none is fixed silently. It reviews every page against D-230's "no filler text" rule (§3.1): no taglines or section-restating sentences, labels staying nouns/numbers, explanations only in tooltips. It uses the open-source **VibeSec** security-review skill as an additional checklist (D-215; vetted and pinned to a commit before use). It also **validates the users and roles** (D-168): every role's effective permissions match its description in §2, the group→role map, the first-owner setup, and the user records themselves. It checks that **the typing gate is green** (D-209): `mypy --strict` over the full security list of §4 with no unexplained ignores, `tsc` strict, no `any` in the API types or client, the generated schema and TS types in sync, every endpoint contract-tested; and **the dependency audit**: `npm audit` and `pip-audit` clean (or each remaining finding listed for the owner), lockfile and hash pins in place, the npm tree still only the §4 packages, base images pinned, no Node in the runtime image, no CDN. Findings fixed and re-reviewed before 8b.
   - **8b Deploy without the Claude connection (with the owner's approval).** The three services on a staging volume that no live runner reads, the session executor disabled; **no internet route** (tunnel or VPN only). Curl checks: no session → 401/login, wrong Origin → 403, a write without the CSRF token or as a form post → 403, the app shell's CSP and headers as in §9.8, health fresh.
   - **8c Live pentest with full code access** against the 8b deployment: auth bypass, setup-code race, password/TOTP brute force, passkey policy bypass (BE flag, attestation, MDS), OIDC flow and group-claim injection, session fixation and lifetimes, CSRF, IDOR across projects and roles, **role-boundary tests (D-168): for each role, a test user tries to reach what the role description says it should not (other projects, global settings, owner-only actions, user management, other users' sessions)**, agent-role escalation via MCP (an agent posing as a task-manager, a direct write outside the §9.6 list, a tampered proposal payload), machine users (a stolen or replayed machine token, a revoked or replaced token, registration-code brute force and race, a session posing as another machine, an interactive session posing as an AFClaude-driven session and back, a machine user reaching beyond its grants), injection, XSS into the TS frontend (user and session content, markdown through `SanitizedHtml`) and CSP bypasses, CSRF against the JSON API (content-type tricks, missing `Origin`, cross-site WebAuthn calls), WebAuthn ceremony replay or challenge reuse, anything auth-related reachable from JS or web storage, headers/CSP, backup and export download, the bridge whitelist (restore and check commands), and a supply-chain review of the shipped bundle (what's in it matches the lockfile, no unexpected network calls). Fixed, re-tested, 8a re-run on non-trivial fixes.
   - **8d Remove the automation pauses, then attach the Claude connection, seed the backlog, open the route (with the owner's approval).** D-235/D-257's fail-stop pause (D-282: a development-phase measure, to find errors and edge cases while nothing public depends on the runner yet) is removed first: every fail-stop pause site becomes alert + continue — a failure still raises an error the owner sees (the alert, the log line, the audit row), but automation is no longer held for it. Found by grepping for the pause helpers: `failstop.fail()` (the fail-stop door used by `keepalive.py`, `dispatcher.py`, `usage_sampler.py`, `usage_review.py`, `docker/at_shim.py`, `inbox_worker.py`, `inbox_api.py` — `grep -rn "failstop.fail(\|import failstop" --include=*.py .`, excluding `test_*.py`) and `store.db_gate()` (the DB-error path, D-171 — `grep -rn "db_gate(" --include=*.py .`); each site's pause call (`fail(...)` / whatever sets `automation_paused` or a project pause off the back of `db_gate`) is changed to alert-and-continue, reviewed one by one, not deleted in bulk. The named exceptions stay as they are, not touched by this step: D-239 (the fail-stop detail decisions: the owner holding a session is a normal skip, not a failure; a failed usage reading still blocks an approved stalled continue; display paths never pause; the sampler keeps sampling while paused; the trust-mark warning and the refresh-poke retry stay as they are) and D-280 (a failed window-start ping is logged only, never an alert or a pause). Then: point the services at the live volume and enable the executor; seed `BACKLOG.md` locally (D-065); then add the public route behind the login.

The temp dashboard's phase strip (D-085) shows these phases incl. the sub-phases and 8a–8d. It also outlines, with a thin pink outline distinct from the current-phase ring, the phase from which an owner preview is possible (D-211, §10.9: phase 6, which contains step 6a) — driven by a `preview_from` field in `status.json` (the step key, e.g. `"6a"`), computed by `export_quickview.py` from a constant (or a task-store marker), not hard-coded in the page.

**Status display (D-166):** the status views show when the next run will take place (date/time, kind, one-line reason, from `pacing.next_run()`), not the budget rule itself; the rule details belong to the threshold/settings view. The shown next run assumes no more usage from now on (D-200: weekly % at each window start = now; the gate there still adds the run cost and the forecast to the reset), with the forecast-based expectation ("With your forecast usage: …") as a smaller secondary line.
