## 5. Runners

### 5.1 One resident runner daemon (D-153, D-173)
`runner.py` replaces supercronic, the `at` shim and the keep-alive watcher. It is one process with an internal scheduler; every job runs in a child process with a timeout, so a crash doesn't stop the loop. Job intervals are settings.

| job | default |
|---|---|
| 10-min pass: cleanup, verification and health checks, plus the owner's approved stalled sessions (decision `continue`), continued right at their limit reset (+ grace) at ANY time of day: no window, no AFClaude budget/pacing gate (the windows are only for AFClaude); the safety preflight still applies (D-206). It starts no task sessions and no runs (D-205). | every 10 min + on wake |
| session-window start tick, the only place runs begin (D-205): a check at each session-window start inside the window (start + k × 5 h: 23:00 and 04:00 by default, never in between; D-202/D-203; a run from the previous start is over by then). The gate decides; if it passes, the start picks the project by rank/priority and continues that project's task-manager, which works its own tasks (today only AFClaude has one; the selection among several is phase 3b). Once per session-window start (dedup key = the window's end date + the session slot); a POSTPONE defers it to last activity + 60 min (D-018), but only until the night's next session-window start, so the run still ends by the window end; later, it is skipped to that start. The last-stretch slot starts (D-020) work the same way. A start whose run begins later (planned late, D-274; postponed) or is held sends, while no Claude session window is open, one tiny context-free Haiku request right at the start, so the session window opens on the schedule (D-277; Claude opens it at the request time floored to 10 min + 5 h); once per start, recorded with the session reset read after it; a failed ping is only logged (D-280: no alert, no pause; setting `window_ping`). | each session-window start / last-stretch slot start |
| fill-up run (D-212, owner: "do a fillup run at t = reset - calculated_time*factor. Set factor default to 110%, but keep editable and allow option to disable"): a run that ended early (the task-manager stops at `session_stop_pct`, D-014) is continued once more before its session reset, at reset − (100 − session %) / measured fill rate (median %/h of the recent runs) × `fillup_factor`, to use the rest of the session window. The one exception to "runs begin only at starts": it continues that run's own session window, never opens a new one. Once per session window, only after a real run in it; skipped when `fillup_enabled` is off, after a limit hit (D-204), outside the window and the last stretch, when a session-window start before the reset continues the window anyway, or when its weekly cost (remaining × session-to-week ratio) exceeds what is left of the run's budget; waits while the run is going, yields to an active owner (D-018) but never past the reset. The plan (start, remaining %, weekly cost or the reason for none) is shown on the dashboard. Built in `fillup.py` (pure) + `keepalive.fillup_pass()`. | planned each minute; fired at its start time |
| stall scan (`stalled.scan`, own tick) | every 3 min |
| usage sampler + pre/post-reset samples | every 15 min + scheduled jobs |
| usage review | when due |
| status snapshot, AFClaude build-log export (§7.7), backups (§11) | each pass / on change / daily |
| WAL archiver (Litestream, §11.1), a supervised child process; its replication lag is part of the health | continuous |

- **Wake:** after any write that the runner must act on (run-now, a waking message to a task-manager (F14), an agent proposal for a task-manager that isn't running (§7.9), window, pause, answer, decision), `actions.py` sends one datagram to `/data/run/runner.sock` after the commit. The runner then reads `action_requests` and settings from the DB. The DB is the truth; a lost wake is caught by the next tick. No polling interval for run-now (D-153).
- Health: the runner writes its last tick per job to `runner_state`; the web container's health check and F5 read it; the container restarts on a stale heartbeat.
- **Exact timing.** A job with a due time (a session-window start, a last-stretch slot start, a postponed start's recheck, a planned fill-up) runs at that time, within seconds: the scheduler sleeps until the earliest due time, not a fixed poll interval (built in the keep-alive watcher: it wakes at the next due time, and refreshes the usage up to 2 min before a planned fill-up so its start does not wait for `/usage`).
- **Start with the container.** The runner starts when its container starts (built today: the entrypoint starts the watcher at once and retries until it runs; the watchdog cron stays as the fallback; `PAUSED` keeps it stopped), never as a second instance.
- Pause (`automation_paused`) stops automatic starts and continues; it never kills running sessions. Built (D-234/D-235, `failstop.py`): any runner failure or timeout sets it itself, with the reason (`automation_paused_reason`, actor `runner:<component>`), and alerts; every runner checks it before a start or continue (a DB that can't be read counts as paused); the owner clears it (`tasks.py automation resume`); the quickview shows it at the top. A project has its own pause too (D-244, `project_pauses`, `automation.set_project`): an inbox error pauses only the project its message was for; a project's checks hold while either is set (`automation resume --project NAME` / `--all`).
- **No continue after a session limit (D-204).** A task-manager (or any AFClaude run) that hits its session limit is done for that run (ideally the task-manager stops before the session fills); nothing continues it at the limit reset. The next session-window start (or last-stretch slot start) decides by its own check, and may continue a run that stopped at a limit (limit hit before 04:00, the next run at 04:00). Only the owner's approved stalled sessions are continued at their reset (D-206).
- Run now (§5.4, D-153) stays immediate.

### 5.2 One continuation path (D-147)
- Every project has exactly one task-manager (D-189), and AFClaude's own task-manager is just the task-manager of the AFClaude project (`projects.manager_session` holds its session), continued like every other project's, only at starts: the session-window start and the last-stretch slot starts (D-205), plus compaction (§5.5) and the fill-up run of a run that ended early (§5.1, D-212); never a stall continue at a limit reset (D-204). There is no global task-manager. The keep-alive watcher's continuation path and its exclusion list (`keepalive_sessions`) go away. `keepalive.py` keeps only reusable pieces (transcript parsing, preflight, budget wiring).
- Per-project session settings: model and effort (default for task-manager sessions: Opus 5.5, high, D-043), permission mode (auto; dontAsk for Haiku, D-047), guard bypass with the hook rules in context (D-044), no `--bg` (D-045), take-over-idle (D-046), archive at the end (D-050), trusted dirs (D-051).

### 5.3 Readable tmux names (D-147)
- `afc-<project-slug>-<role>`: `afc-afclaude-task-manager`, `afc-stall-<title-slug>-<id4>`, `afc-review` (no per-task sessions, D-205). Charset `[a-z0-9-]`, ≤ 40 chars, a short suffix only on collision. The same string is the RC `--name`.
- Runners find their sessions through `driven_sessions` (tmux name ↔ session id), never by a name regex (today `ka-[0-9a-f]{8}`).

### 5.4 Run now (D-153, D-036, D-173)
- Kinds: `continue_now` (one stalled session), `work_on_now` (a project: its task-manager, with its next ready stage), `review_now`; a waking `task_manager_message` (F14) is delivered the same way.
- Who: owners, and managers for their own project (D-184, D-190). Editors can't force an immediate run; viewers can't request anything. `review_now` (the usage review, global) is owner only.
- Run-now **skips the time window and the budget check** (incl. the session-usage stop) and starts **immediately**: the write queues the request and wakes the runner (§5.1). It still passes the safety preflight (never take over an RC-server thread or a live holder; never fork a session). It also runs while automation is paused (pause is about the automatic schedule; there is no concurrency cap to be limited by, D-205/D-206); the button warns when the session limit is nearly used up.
- Feedback: the request row moves queued → started (tmux name) / refused (reason), shown live on the card.

### 5.5 Compaction hand-offs (D-144, D-155, D-233, D-238, D-307)
Hand-offs and compaction are **per driven session** (one `driven_sessions` row). **When (D-238, replacing D-191/D-218's "at a start, if the conversation ran before the session window"; threshold and mid-run: D-307):** the expensive event is the first request after the 1-hour prompt cache expired, which re-writes the whole context (the 14.10. evaluation: 38 re-reads ≈ 46% of the task-manager's usage), and a long context makes every request dearer. So the runner compacts **while the cache is still warm**: (a) when a run ends (D-224), (b) after ~50 min without a request (also after the owner's daytime chats) and (c) **during a run** (mid-run) at the first point where the session is idle at its prompt, each only if the context is at or above the setting **`compaction_threshold_tokens` (150k, D-307)**. Below it no compaction. (It replaced D-238's computed break-even C* = ((S + H)·o + 2·B·w) / (w − r) from the stored cost model, ≈177k, which the compaction records and the quickview still show; the cost model is a telemetry record, `cost_model`, audited action `cost_model.set`, re-fitted from the 15-min `/usage` samples by the monthly usage review, `compact_timing.py fit --store`.) (a) and (b) never while a run uses the session, a turn or subagent is running, or the owner is typing (attached terminal keystrokes, a draft in the input box); never at a start (a start waits for a running compaction). (c) needs only the session's own turn to have ended: **background subagents may still be working** (the task-manager almost always waits on them, so waiting for them too would let the context grow far past the threshold); they survive the compaction, their notifications arrive after it, and the hand-off lists them as in flight. Its guards: not within 60 min of the last compaction, only once the context was below the threshold since it (no loop), not within 10 min of the owner's typed or dashboard message, the owner not typing, the cache not about to expire, no start due within 40 min, the session limit below 97%. After a mid-run compaction the session gets `compact_after_run.md` (the run goes on with its budget, window end and pacing) instead of READY; it is no run end.
1. **Save prompt, directly before the compaction (D-233).** `session_end_save.md` (park the current step, commit, write the hand-off with every subagent still running, its agent id, task and branch; the compaction follows right after the reply); the runner waits for the new hand-off (only one written after the prompt counts). A reply without one gets the save prompt re-sent once, saying no new hand-off was found (`session_end_save_retry.md`); a second reply without one is an error (point 4). It holds everything up to then, also the owner's interactive chats. **A turn after the hand-off (D-307):** a subagent's task notification (or the owner's message) can start a turn between the hand-off and the `/compact`. The runner waits for that turn to end (≤ 10 min, else an error), and if anything reached the session after the hand-off was written (a prompt, a subagent's hand-back or other peer message, or a message queued for it or delivered into its turn) and the session did not write a newer hand-off after it on its own, it asks for the hand-off again (`session_end_save_refresh.md`: a hand-off newer than the out-of-date one, waited for like the save prompt); at most 3 times, then an error. Only then `/compact`.
2. **Structured hand-off.** The session writes it through MCP (`afclaude_handoff`) into `handoffs`: summary, done, in progress, next steps, open question ids, decision ids, files touched, notes (JSON, size-limited). One open hand-off per tmux session; a new one replaces that session's open one. The task-manager's is the project's hand-off; an agent's hand-off is one of its direct writes and is listed in its run summary (§7.9).
3. **Compact, then give the hand-off back.** The runner sends `/compact`, waits for the compaction marker in the transcript, then sends `compact_after.md` with the hand-off (`compact_resume.md`); the session answers without starting work and the hand-off is marked consumed.
4. Any failure or timeout on the way (no new hand-off, a busy session, a turn after the hand-off still running after 10 min, a hand-off still out of date after 3 asks, no marker, a send failure, no reply, a DB error) is an error (D-234/D-235): the compaction stops there, the attempt is recorded and not retried, an alert, automation paused. An older hand-off is never given back in place of the fresh one.
- The dashboard shows the latest hand-off per session (F6) and the task-manager's per project (F9). Hand-offs are in the backup (§11) and let a moved install resume cleanly even when a transcript can't be resumed.
- **As built (D-214, D-238; in today's keep-alive watcher, `keepalive.compaction_pass` + `compact_timing.py`; phase 3c's runner reuses it). The age rule and the start-time compaction described next were the first build, replaced by D-238 above:** `handoffs` table (id, session_id, project_id, created_at, created_by, body JSON {summary, done, in_progress, next_steps, owner_messages, in_flight, lessons, working_notes (D-305, optional), open_question_ids, notes}, consumed_at, consumed_by_start; additive, no schema-version bump); actions `handoff.write` (any session its own, D-185) and `handoff.consume` (runner only), MCP `afclaude_handoff`, CLI `tasks.py handoff write|show`. The rule (D-218, replacing the first build's tmux pane start time): the timestamp of the first user/assistant entry of the session's transcript (only the head of the file is read) is before the start of the session window that ends at the start (= the start − one session length; 15 min slack); no transcript or no timestamp = no compaction. At a start that continues the session by send-keys (window-start, postponed start, last-stretch slot; never a fill-up): wait until the turn ended (≤ 5 min, else neither save nor compaction this time), the save prompt (D-233; `keepalive.save_before_compaction`), wait for a new `handoffs` row of the session (≤ 10 min; given up early once the session answered and went idle without one), `/compact <prompts/compact.md>`, wait for the `compact_boundary` / `isCompactSummary` entry in the transcript (≤ 10 min), then the continue prompt with the hand-off that save wrote inserted (not via a `{handoff}` placeholder: `prompts/compact_resume.md` is inserted after the continue text), consumed (with older ones) once sent. One helper, `keepalive.compact_with_handoff()`, runs the save → `/compact` → hand-off steps (the live test calls it). Any failure or timeout on the way (a busy session, no new hand-off or a reply without one, a send failure, no marker, the saved hand-off not found, a DB error) aborts the start (D-234, owner: "no run until fixed"): no `/compact` after a failed save, no continue, the start recorded as `start-failed`, an alert, and `automation_paused` set with the reason (`failstop.py`, D-235) until the owner clears it (`tasks.py automation resume`); an older hand-off is never injected in place of the fresh one (the stale label of the first D-233 build is gone). The save result is in the start's record (`compaction.save`: status, handoff_id, active, sent_at). A start that has to resume the session into a new tmux session (no live one) is not compacted at that start (nothing to type `/compact` into before the continue), but the conversation keeps its age: the next send-keys start saves and compacts it.
