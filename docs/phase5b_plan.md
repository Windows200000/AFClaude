# Phase 5b: containers, the host kit and the host checks (implementation plan)

Plan for design §4, §9.7, §9.8 (container isolation), §10.1, §10.2, §10.5, §10.6 / §13 step 5b: one image with three services (web, runner, MCP), a compose file for plain docker and Coolify, the minimal env, the master key, the MCP server in a container with the remote transport and machine-token auth, the host checks as a runner job and a CLI, and the cut-over of this install from today's single container. Sessions stay on the host behind the SSH bridge. Plan only: the held runner branches (3a S2–S6) rewrite `docker/compose.yml`, `docker/crontab` and `docker/entrypoint.sh`, and S7–S9 (not built) finish the job; 5b starts where S9 leaves the container (§4). Each step in §5 is one worker branch.

Binding inputs: D-120 (the container is the manager and bundles everything that isn't machine-specific; the host executes), D-121 (the owner installs the bridge), D-163 (everything in containers incl. the MCP server; Coolify or plain docker; minimal env, the rest in the DB), D-164 (sessions on the host; the dashboard validates tmux, Claude Code, its login and the bridge), D-146 / D-161 (settings and state in the DB), D-180 / D-187 (`AFCLAUDE_DATA` required, no default; built with 5c B7), D-195 / D-198 (machine users; remote MCP over HTTPS at `/mcp` through the proxy, tunnel or VPN only until 8d; on the host the token only identifies), D-209 (mypy --strict for `docker/host_exec.py`, the MCP transport and the key code), D-217 (every permission AFClaude needs is in the repo), D-235 / D-282 / D-283 (fail fast: alert + pause; the pauses become alerts before release; the task-manager clears a pause after investigating), D-257 (deploys drain first; no rebuild within 30 min of a session-window start), D-007 (existing options first, §2).

## 0. Already decided

- **One image, three services** (design §10.1): `afclaude-runner` (the resident runner as the main process, 3a S8), `afclaude-mcp` (stdio through `docker exec` on this host, streamable HTTP for other machines), `afclaude-web` (in 5b: `health` and the temp dashboard's inbox API; the dashboard itself is 6a). All three mount only `/data`; the runner also gets the bridge key and the host's public host key. Read-only root fs, non-root UID, `cap_drop: [ALL]`, `no-new-privileges`, no docker socket, no published port in the base file.
- **The inbox API moves to `afclaude-web`.** After 3a S7 `inbox_api.py` only serves HTTP, stores the message and wakes the runner (the delivery is the runner's `inbox` job), which is exactly the web service's role (record intent, wake the runner, never execute). The quickview's nginx keeps reaching it through the unix socket in the data dir.
- **No transcript mounts.** Design §10.1 gives the runner `/data` and the bridge keys only. Today's read-only mounts of the host's `projects/` and `sessions/` are replaced by batch bridge reads (§3.4). Reason beyond the design: the Claude config dirs are chosen at setup (5d), after the containers exist, so a mount would need a redeploy with new env per install.
- **Every host-side AFClaude command runs in a container** (D-163). The host's `.venv` MCP registration, `python3 tasks.py` and the SessionStart hook's `python3 keepalive.py --session-rules` on the host checkout are replaced by one host wrapper `afclaude` (part of the host kit, §3.2) that runs `docker exec -i` into `afclaude-mcp`, passing only the identity env 5a needs (`CLAUDE_CODE_SESSION_ID`, `AFCLAUDE_AGENT_ID`, `CLAUDE_GUARD_DISABLE`, the machine token). This also ends the host's older SQLite (3.26, design 5c §0) writing the live DB, and the "host process with an old checkout" risk of 5c B4. The repo's `.claude/settings.json` allow rules change with it (D-217).
- **Stable container names** (`container_name: afclaude-runner|-mcp|-web`). The stdio registration and the wrapper `docker exec` by name. Coolify honours a custom name for compose services and then drops rolling updates, which AFClaude must not have anyway (two runners must never run).
- **The master key** follows design §10.2: `AFCLAUDE_MASTER_KEY` if set, else generated once into `/data/master.key` (mode 0600). Nothing in the DB is encrypted with it in 5b (TOTP seeds and the OIDC secret come with 6a/6b); 5b builds the key handling and the envelope helper, 5c B2 wraps it into bundles.
- **`AFCLAUDE_PUBLIC_URL` is optional until 6a.** Design §10.2 marks it required; before 6a nothing needs it except the remote MCP registration command, and before 8d there is no public URL (D-157). 6a makes it `:?` in compose.
- **Fail fast** (D-235): a host check that fails, a service that can't start, a key mismatch: alert + pause (`failstop.fail`, components `hostcheck`, `container`, `masterkey`), never a degraded start. D-282's pre-release step turns them into alerts like every other site.

## 2. Existing options checked (D-007)

- **Coolify's compose conventions** (its docs, checked 22.10.): `${VAR:?}` makes a variable required and blocks the deploy until it is filled (the same syntax plain compose uses, so one file serves both: D-180's "nothing starts without `AFCLAUDE_DATA`" holds in both); `${VAR:-default}` prefills; absolute bind mounts are kept, relative ones are rewritten under Coolify's resource directory, so every mount here is absolute or a variable; a `healthcheck` decides the resource's status; Coolify adds its own network and proxy labels unless "raw" mode is chosen; `ports:` bypasses its proxy and is discouraged (the base file publishes nothing); magic variables (`SERVICE_FQDN_*`, `SERVICE_PASSWORD_*`) are Coolify-only and not used, so the file stays plain-docker compatible. Two Coolify-specific risks are handled in §3.1: the network is Coolify's, not ours (the bridge `from=` becomes configurable), and a Coolify deploy recreates the containers without `tools/deploy.py`'s drain (D-257).
- **Remote MCP auth:** the SDK's `MCPServer(token_verifier=…)` (resource-server mode: it checks the bearer token on every request and returns 401 with RFC 9728 metadata otherwise) with our own verifier over 5a's `machine_tokens`, instead of a hand-written ASGI middleware. A full OAuth authorization server is not needed: D-195/D-198 chose a per-machine token sent as `Authorization: Bearer`, which Claude Code supports with `claude mcp add --transport http … --header`.
- **Host checks:** Claude Code's own `claude auth status` (JSON, exit 0 = logged in, names the config dir in use) replaces `/usage` as the login check; `claude doctor` (read-only: install health, settings-file errors, Remote Control eligibility) is one check; `claude --version`. tmux and disk checks are plain commands. No monitoring framework (Prometheus exporters, healthchecks.io) fits a whitelisted SSH bridge; the checks are ~10 small functions.
- **Dependency pinning:** `pip-compile --generate-hashes` (pip-tools, run in a throwaway container from the same base image) for a committed `docker/requirements.txt`, installed with `pip install --require-hashes`; the base image by digest. `pip-audit` runs in 8a.
- **Master key:** `cryptography`'s AES-256-GCM with HKDF per purpose (already in the image through `mcp`); no extra library, no external KMS (an optional env value covers "the key lives elsewhere"). Docker/compose `secrets:` was considered for the key and the bridge key, but Coolify's support for file secrets is limited to its own file mounts; a mounted file path given by env works on both.

## 3. Design details

### 3.1 Compose (`docker/compose.yml`)
- Services `afclaude-runner`, `afclaude-mcp`, `afclaude-web`, one image `afclaude:<version>`; `/data` = `${AFCLAUDE_DATA:?AFCLAUDE_DATA is not set: choose the data directory (see setup)}` in all three (with 5c B7).
- Env: `AFCLAUDE_DATA` (required), `AFCLAUDE_PUBLIC_URL` (optional until 6a), `AFCLAUDE_MASTER_KEY` (optional), `AFCLAUDE_BRIDGE_HOST` (default `host.docker.internal`). The bridge user, the host's Claude binary path and the check intervals are DB settings (section Host); the bridge key and host key are files in the data dir (`/data/bridge/`, written by the host kit install, §3.2), so no extra mount variable exists.
- `afclaude-runner`: `restart: unless-stopped`, `stop_grace_period: 90s`, `extra_hosts: host.docker.internal:host-gateway`, health check = the runner's loop heartbeat in `runner_state` (3a S8). `afclaude-mcp`: health = the HTTP listener answers. `afclaude-web`: health = `GET /health` (no secrets: DB reachable, runner heartbeat age, schema version).
- No fixed subnet in the base file. The bridge's `from=` is set at install to the network the runner actually uses (the host kit reads it from `docker network inspect` of the compose project, or the owner passes it), and the host check "bridge reachable" catches a mismatch. `docker/compose.subnet.yml` keeps today's pinned subnet as an optional override for this host.
- `docker/compose.tunnel.yml` (optional): publishes the MCP HTTP port on the host's loopback only, for an SSH tunnel before 8d. Not in the base file.
- **Coolify deploys and D-257.** A Coolify deploy recreates the containers on its own schedule (a push with auto-deploy on), without the drain or the "not within 30 min of a start" guard. The runner already exits cleanly on SIGTERM within its stop grace and catches up at boot (3a); the README's Coolify section says to switch auto-deploy off and deploy with the button (or `afclaude deploy-check`, which prints whether now is safe). On plain docker `tools/deploy.py` stays the only deploy command, extended to the three services.

### 3.2 The host kit and the bridge
- **Host kit** = everything AFClaude needs on the host that can't run in a container: `host_exec.py` (the forced command), `ka_resume.sh`, the `afclaude` wrapper, the hook scripts (delegation reminder; the SessionStart rules hook becomes `afclaude hook session-rules <part>`), `trust_dirs.sh`. Installed by `install_host_bridge.sh` (run by the owner, D-121) into a fixed versioned directory outside any checkout (under the owner's local share dir, `…/afclaude/host-kit/<version>/`, plus a `current` link); the `authorized_keys` line points at `current/host_exec.py`. A repo move (5e) or a new checkout then changes nothing on the host.
- **Host config** `…/afclaude/host.json` (mode 0600, written by the install and by the setup through a whitelisted `host-config set` command): the allowed roots (today the workspace root; from 5d the working root and AFClaude's config dir), the Claude binary path, the repo path of the kit's source. `host_exec.py` reads it on every call, because sshd passes no env; its hard-coded root, repo and binary constants go.
- **Version:** `HOST_KIT_VERSION` in the kit and in the image; the bridge command `kit-version` returns it with the whitelist hash; a mismatch is the first host check (fail: "re-run the host kit install"). A new whitelist command means a new kit version; the image refuses (fail fast) to call a command the installed kit doesn't list.
- **The bridge key** is generated by the install into `/data/bridge/` of the data dir (mode 0600, owned by the container UID) instead of `docker/secrets/` in the repo, so it travels with nothing but the data dir and never with the repo.

### 3.3 MCP in its container
- `afclaude-mcp` runs `afclaude mcp serve`: the streamable HTTP app (`MCPServer.streamable_http_app()`) on an internal port, `token_verifier` = 5a's machine-token check (hash lookup, constant-time compare, `last_seen` update, revoked or unknown → 401 and an audited refusal). The principal from the token goes into `mcp_server.act` per request (5a A2's `identity.resolve` with the transport's claims). No route through the proxy until 8d (D-157/D-198); before that only `compose.tunnel.yml`.
- Stdio on this host: `docker exec -i -e AFCLAUDE_MACHINE_TOKEN -e CLAUDE_CODE_SESSION_ID afclaude-mcp afclaude mcp stdio`, one process per interactive session as today. The token comes from the machine's token file (5a §3.3), read by the host wrapper, never written into a Claude config file in clear (the registration's `env` entry names the wrapper, which reads the file).
- The registration itself is a user-level change in the owner's interactive Claude config, which AFClaude never edits: `afclaude setup` prints the exact `claude mcp add --scope user …` line for the owner (as `mcp_register.md` does today). AFClaude's own sessions get theirs in AFClaude's config dir (5d).
- The remote registration endpoint (`machines/register`) stays with 6a's API; until then a remote machine is registered on the host (`afclaude machine code` + `register`, 5a) and its token copied over the tunnel by the owner.

### 3.4 Transcript and session reads through the bridge
- New kit command `transcripts <config-dir-id> --changed-since <ts> [--head N] [--tail N]`: one call returns, for every transcript under that config dir's `projects/` changed since the timestamp, its path, size, mtime and the parsed head/tail entries the readers need (the stall scan's limit notice, the compaction marker, the first entry's timestamp, the last entry's kind). `sessions <config-dir-id>` returns the running-session files. Limits: allowed config dirs from `host.json` only; output capped (size and entry count) with an explicit "truncated" flag the caller treats as an error (D-235).
- **Project files the runner reads or writes** (today through the read-only repo mount and the symlinks into it): the scheduled docs import reads `PROGRESS.md` / `GOALS.md` / `EXCEPTIONS.md` of the project whose directory is the repo, and the decision import reads `DECISIONS.md` (until 4b retires it). New kit command `doc-files read <project dir> <name>…`: only those names, only in a project directory under the allowed roots. The export (`tasks.py doc export`, D-181's only file output) runs from a session through the host wrapper: the container returns the `check_public`-checked texts as JSON and the wrapper writes the files on the host, so no container ever writes into a checkout.
- Readers switched: `stalled.py` (scan), `keepalive.py` (`PROJECTS_DIR`, idle/turn detection, compaction marker, preflight's `sessions/` read), `usage_sampler.py`, `compact_timing.py`; each keeps its file-reading core and gets the bytes from the batch result in the container (the host path stays the default when `AFCLAUDE_IN_CONTAINER` is unset, for host-side tests).
- K0 measures the batch call on this host's transcripts (expected well under a second per 3-min scan; the slow part is reading, which the host does either way).

### 3.5 The master key (`masterkey.py`, mypy --strict)
- `ensure()` at every service start: env value (base64, 32 bytes) or `/data/master.key` (created once with `O_EXCL` + an flock, so the three services can't race). Both present and different → refuse to start.
- `meta.master_key_check` = HMAC of a fixed label: written on first use; a key that doesn't match (a restored DB without its key, a wrong env value) → refuse to start with a clear message (fail fast), never a silent new key.
- `seal(purpose, plaintext)` / `open(purpose, blob)`: AES-256-GCM, a per-purpose key from HKDF, format `v1:<key-id>:<nonce>:<ct>`; rotation (`afclaude key rotate`, re-seals every sealed column) is listed for 6a when the first secret exists.
- The key file is in the data dir, i.e. it protects DB copies that leave without it (a stray DB file, a support copy); backups carry it wrapped (5c B2).

### 3.6 Host checks (`hostcheck.py`, design §10.5)
- `host_checks` table (additive): one row per check (name, status ok|warn|fail|skip, detail, fix hint, ran_at, duration, kit version); every run also appends an `app_log` line. Written through `actions.py` (`hostcheck.record`, runner only).
- Checks in 5b: kit version and whitelist hash; bridge reachable + host key (the ssh handshake); tmux present and can create and kill `afc-check`; Claude Code installed and its version (warn above the tested version, a DB setting); logged in, per config dir in use (`claude auth status`, `authMethod` = `claude.ai` expected); usage readable and fresh (the usage-cache call vs the latest sample); `claude doctor` clean (settings errors = fail, Remote Control not eligible = warn while every RC category setting is off, else fail, D-042/D-269); MCP answers `list_tools` through the stdio form; disk space of the data dir and the host's Claude dir (warn / fail thresholds as settings); clock drift container vs host (warn > 5 s, fail > 60 s). The working root, trust, permission-setup and `CLAUDE.md` checks come with 5d (they need its settings). End-to-end session: on demand only (`afclaude host check e2e`, a Haiku session in tmux `afc-check-e2e`: start → prompt → reply → kill), never on a schedule.
- When: a runner job hourly and right before each session-window start (3a's `window_start` calls the blocking subset first); `afclaude host check [name]` on demand; the setup and 5d's post-restore validation call the same function.
- A **fail** of a blocking check (kit, bridge, tmux, Claude installed, logged in, MCP) → `failstop.fail("hostcheck", …)` (alert + pause; the start is not attempted). A warn is shown and logged, no alert. Each check has a timeout; a timeout is a fail.

## 4. Order and dependencies

- **Before K1:** 3a S2–S9 merged and deployed (they own the Dockerfile, compose, entrypoint and crontab until S9 removes supercronic); 5c B1 merged (the data-dir layout is shared). K0 and K3 have no dependency and can run any time.
- K1 → K2 → K4 → K7; K3 before K4 (the services call `ensure()`); K5 needs 5a A1/A2 (tokens, `identity.py`) and K4; K6 needs K2 (kit commands) and the runner live; K7 needs K1–K6 and 5c B7 (`AFCLAUDE_DATA` required: built together, design 5c B7).
- **Live code:** K2's `host_exec.py`, K4's entrypoint and K6's start hook change what the live system runs: built in worktrees, deployed between runs with `tools/deploy.py` (D-257). K4's reader switch (§3.4) touches `keepalive.py` and `stalled.py`: never in parallel with another step editing them.
- **5d builds on K2/K6:** the kit's `host.json` gets the working root and config dir; the host checks get the root and config checks; the export reads through the same kit.
