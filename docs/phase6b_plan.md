# Phase 6b: passkeys and OIDC (implementation plan)

Plan for design §13 step 6b, with the parts of §2 / §9.4 (owners and OIDC group grants), §3 F11 (account view), §7.1 / §7.2 (secrets, auth tables), §8 (the WebAuthn ceremonies and the OIDC redirect flow from the TS client, step-up), §9.3 (login methods, the factor rule, the phone caveat), §9.5 (session lifetimes, remember-device, step-up, rate limits), §9.8 (CSRF, CSP, nothing auth-related in the browser), §10.2 (the public URL as RP ID and redirect URI), §10.9 (owner previews) and §12 (auth tests) that it builds: python-fido2 with the FIDO Metadata Service (MDS3), the BE/BS rules and warnings, hardware-bound enforcement, synced passkeys as one factor, the ceremonies from the TS client, Authlib-based OIDC with group claims → grants, back-channel logout, step-up re-authentication, remember-device and recovery rules, and F11. It builds on phase 6a (`docs/phase6a_plan.md`, branch `phase6a`, not merged yet) and on 5a's users and grants (`docs/phase5a_plan.md`). Each step in §5 is one worker branch.

Binding inputs: D-071 (generic SSO from any provider plus username/password), D-150 (OIDC with the provider's groups; password login only with 2FA; the owner asked for hardware-only passkeys), D-159 (hardware-bound passkeys enforced, checked against the FIDO metadata; a non-hardware passkey warns that it isn't hardware-bound and still needs 2FA), D-149 / D-172 / D-183 (first registration is owner; several owners; owner grantable through an OIDC group; the last owner not granted by a group can't be removed), D-162 / D-179 (session lifetimes are settings with secure, unobtrusive defaults; remember-device 7 days), D-157 / D-072 / D-073 (no internet route and no Claude connection before gates 8a–8c; reachable behind this login afterwards), D-168 (8a validates users, roles and the group map; 8c tries role and passkey-policy escalation), D-154 (one write path with audit), D-208 / D-209 (Python keeps auth, the TS client only renders and converts; mypy --strict and TS strict), D-211 (preview after every UI step), D-230 (labels are nouns, explanations in tooltips), D-235 / D-282 (fail fast until the pre-release step), D-007 (existing libraries first), D-263 / D-279 (owner questions in plain words, in full).

## 0. Already decided

- **python-fido2 2.2.1 for WebAuthn, Authlib 1.9.1 (+ its dependency joserfc 1.7.7) for OIDC.** Both depend only on `cryptography` (50.0.1, already in the tree; fido2 accepts < 52, so a `cryptography` bump past 51 waits for fido2). fido2 and joserfc ship `py.typed`; Authlib doesn't, so only one module (`dashboard/auth/oidc.py`) imports it, behind typed wrappers, with `[mypy-authlib.*] ignore_missing_imports` and no `type: ignore` elsewhere. Pinned with hashes in W10's `requirements.txt` (6a). Library research: §2.
- **Authlib's protocol pieces, not its Starlette client.** The Starlette client needs `httpx` (the tree has only `httpx2`, through `mcp`) and keeps the flow state in Starlette's `request.session` (a signed client-side cookie, which 6a ruled out). 6b uses Authlib's discovery metadata validation (`oidc.discovery`), PKCE (`oauth2.rfc7636`), ID-token claims validation (`oidc.core.CodeIDToken`: iss, aud, azp, exp, iat, nonce, at_hash, auth_time / max_age) and RFC 9207's `iss` check; joserfc verifies signatures against the provider's JWKS; the three HTTP calls (discovery, JWKS, token) go through `httpx2` (already in the tree), with fixed timeouts. Our own flow state lives in the DB (§3.6).
- **fido2's `Fido2Server` does the ceremony checks, AFClaude adds the rest.** fido2 checks type, challenge, RP ID hash, UP, UV and the signature, and verifies attestation through `MdsAttestationVerifier`. It does **not** check the sign counter, the BE/BS flags, the metadata entry's key protection or the blob's certificate dates, and its default origin check accepts any subdomain: AFClaude passes an exact-origin check (the origin of `AFCLAUDE_PUBLIC_URL`) and does the rest in `passkeys.py` (§3.2–§3.4).
- **The MDS3 blob is verified with path building to GlobalSign Root R46.** FIDO moved the blob's signing root from GlobalSign Root CA – R3 to Root R46 in August 2026; the blob's `x5c` now carries the leaf, the intermediate and an R3→R46 cross-certificate (valid until 18.03.2029). fido2's `parse_blob` verifies the chain strictly in order, which fails with R46 as the anchor. `mds.py` verifies the chain with `cryptography`'s X.509 path validation (validity dates included) against the pinned R46 root (DER committed, its SHA-256 checked by a test), verifies the JWS signature with the leaf key, then parses the payload with fido2's `MetadataBlobPayload`.
- **Passkeys are discoverable credentials** (`residentKey: required`, `userVerification: required`, `attestation: direct`). Login with a passkey asks no username (empty `allowCredentials`), so nothing reveals which usernames exist. As a second factor or for step-up, the user is known and `allowCredentials` lists that user's passkeys. The WebAuthn user handle is a random 32-byte value per user, never the user id or the username.
- **Exactly one OIDC provider per install**, configured in Settings; tables are keyed by issuer, so a second one is a later change, not a migration.
- **The OIDC start is a JSON write, not a GET.** `auth/oidc/begin` (CSRF-checked like every write) returns the provider URL and the client navigates to it; the callback (`/auth/oidc/callback`) stays the one state-changing GET (§9.8). Design §8's `/auth/oidc/start` is corrected in P9.
- **Browser routes outside `/api/v1`.** 6a's endpoint table only takes JSON routes under `/api/v1/`. The callback (GET, redirect) and back-channel logout (POST, form-encoded, server to server) go into a second, equally closed table, `BROWSER_ROUTES`, routed before the app shell's catch-all; the route-table test covers both tables.
- **Provider tokens never reach the browser and are not kept.** The access token is used once (userinfo, when the groups aren't in the ID token) and dropped; AFClaude stores only the identity (issuer, sub), the ID token's `sid` (for back-channel logout) and the time of the login. No refresh tokens.
- **The client secret is a write-only setting**, encrypted with the master key (§7.1); the API returns only whether one is set.
- **Remember-device after a synced passkey:** §9.5 says a remembered device skips the second factor after a *password*. A synced passkey is a stronger first factor than a password, so it gets the same treatment; never the first factor, never step-up. *Interpretation, 8a checks it.*
- **Failures fail fast** (D-235): a failed MDS refresh is an alert, and as a runner job also a pause (`failstop.fail("mds", …)`, removed at the pre-release step, D-282); a ceremony or callback that fails a check is refused, audited, and rate-counted; nothing is downgraded silently (an unverifiable passkey is labelled synced *and the user is told before it is saved*, §3.3).

## 3. Design details

### 3.1 Module layout
`dashboard/auth/` (mypy --strict): `mds.py` (fetch, verify, store, look up), `passkeys.py` (the policy: classification, assertion checks; pure over fido2's types), `webauthn.py` (the ceremonies over `Fido2Server` and the challenge store), `oidc.py` (the only Authlib importer: discovery, authorization URL, callback, back-channel token), `stepup.py`, `factors.py` (6a's factor rule, extended). Endpoints in 6a's `routes.py` table; `BROWSER_ROUTES` beside it. `dashboard/auth/fido_mds_root_r46.der` (public root certificate).

### 3.2 MDS3 (P1)
- **Fetch:** `https://mds.fidoalliance.org/` (`mds3.` answers 301 to it since 2026; redirects are not followed) (one GET, timeout 30 s, at most once an hour: FIDO's rate limit). Daily as a runner job (`mds_refresh`) once the runner is live; until then, and whenever the cached list is missing, `afclaude auth mds-refresh` (CLI) or the web process on a registration (the same function).
- **Verify:** path to the pinned R46 root with validity dates (§0), the leaf valid as a TLS server certificate for the MDS host (else any R46-issued certificate could sign a blob); JWS signature with the leaf key (algorithm from the header, only ES256/RS256 accepted); `no` (the blob serial) must be ≥ the stored one (lower = a rollback, refused and alerted; equal = no new list, but the check is recorded, see Store); `nextUpdate` read. An entry fido2 can't parse (live since 2026: a passkey provider's MDS 3.1 statement without `userVerificationDetails` / `attachmentHint`, which fido2 2.2.1 requires) is skipped: its model counts as unknown (never hardware; a problem status in its raw reports still refuses it), and the skipped entries (AAGUID or key identifiers, description, reason) are kept as warnings of the verified list for the dashboard to show. Any other structural error refuses the whole blob. *Task-manager decision, 22.10.*
- **Store:** `mds_cache` (additive): blob serial, `nextUpdate`, fetched at, sha256, the payload (compressed), entry count, and `checked_at`: a fetch that finds the same serial records "checked, same serial" with its time (the list's age for `auth_mds_max_age_days` counts from the last check, not from the first fetch, else hardware logins would need a second factor after 30 days under a current list). Written through `actions.py` (`auth.mds_store`, actor `runner:mds` or `cli`). The web process reads the newest row.
- **Which entries count:** an entry is usable for "hardware" when its newest status report is a certification or `UPDATE_AVAILABLE` / `NOT_FIDO_CERTIFIED` (not a problem status), none of its reports is `REVOKED`, `USER_VERIFICATION_BYPASS`, `ATTESTATION_KEY_COMPROMISE`, `USER_KEY_REMOTE_COMPROMISE` or `USER_KEY_PHYSICAL_COMPROMISE` (fido2's default filter removes only `REVOKED`), and its metadata statement's `keyProtection` is only `hardware`, `secure_element` and/or `tee` (D-150: "physical or stored in a secure part of a device"; `software` or `remote_handle` never count), and it is not a syncing passkey provider (`multiDeviceCredentialSupport` `explicit` / `implicit`).
- **Stale list:** past `nextUpdate` + 7 days, every new registration is refused, synced ones too (*task-manager decision, 22.10.*: the problem-status refusal of §3.3 runs on the list for every registration, so no registration is classified on old data), with "the hardware check is out of date" and an alert (never classified on old data, never quietly saved as synced). Logins with an already registered hardware passkey keep their classification and are checked against the newest verified list; past `auth_mds_max_age_days` (setting, default 30, 7–90) they need a second factor, and the login dialog says why. *Interpretation of D-235, flagged in the report.*

### 3.3 Registration and classification (P2, P3)
- `auth/passkeys/register/begin` (full session, step-up, or the setup flow): options with the user's random handle, the RP (`id` = host of `AFCLAUDE_PUBLIC_URL`, `name` "AFClaude"), `excludeCredentials` = the user's passkeys, ES256 / EdDSA / RS256, `residentKey: required`, `userVerification: required`, `attestation: direct`, extension `credProps`, timeout 5 min.
- `…/register/finish`: fido2 verifies (exact origin, challenge, RP ID hash, UP, UV; attestation through the MDS verifier when the format isn't `none`), then `passkeys.classify()`:

| result | rule |
|---|---|
| **refused** | BS = 1 with BE = 0 (invalid flags); UV not set; `credProps.rk` false; an AAGUID whose entry has a problem status (§3.2); the credential id already registered (to anyone) |
| **hardware** | BE = 0, BS = 0, attestation verified to an MDS root for this AAGUID (or key identifier), the entry usable (§3.2), the list not stale |
| **synced** (counts as one factor) | BE = 1; or BE = 0 with attestation `none`, self attestation, an AAGUID not in MDS, or a chain that doesn't verify (the user declined the browser's attestation prompt, or the device isn't listed). The stored reason says which. |

- A synced result is saved as **pending** (unusable) and returned with the warning (D-159), in plain words: "This passkey is not hardware-bound (it can be copied to other devices). You will still need a second factor when you sign in with it." Confirm → `…/{id}/confirm` makes it usable; cancel or 10 min without a confirm deletes it. A hardware result is usable at once. The client also shows a short note *before* the ceremony on a phone: phones create synced passkeys; a security key over NFC or USB-C gives a hardware one (§9.3's phone caveat; text in a tooltip, D-230).
- Stored (`passkeys`, additive; design §7.2's `credentials` row for WebAuthn becomes its own table, P9 corrects the text): user, credential id (unique), COSE public key, sign count, AAGUID, class, class reason, BE, last BS, attestation format, MDS serial and entry description at registration, transports, label (default: the MDS description or "Passkey"), created, last used, disabled at / why, pending until. Writes through `actions.py` (`passkey.register`, `.confirm`, `.rename`, `.remove`, `.disable`), audited; adding or removing a passkey revokes the user's remembered devices (§9.5).

### 3.4 Login, second factor, assertion checks (P2, P3)
- `auth/passkeys/login/begin` (public, pre-session; no username) → `…/login/finish`: the credential is found by its id and the user handle must match. `auth/passkeys/factor/begin|finish`: the pre-session's user is known (after a password, 6a), `allowCredentials` = that user's usable passkeys.
- Checks beyond fido2 (`passkeys.check_assertion`): UV set; **BE equals the stored BE** (BE never changes for a credential: a change is refused, the passkey disabled, an alert); BS = 1 is impossible with BE = 0 (refused); the **sign counter**: when the stored or the new value is non-zero, the new one must be greater, else refused as a possible clone, the passkey disabled and an alert (synced passkeys usually report 0 / 0, which passes); for a hardware passkey, its AAGUID's entry in the newest list must still be usable (a newly revoked or compromised model: refused, disabled, alert, and the user is told to remove it).
- Result as a factor (6a's factor rule, extended in `factors.py`): a hardware passkey with UV completes the login alone; a synced one is one factor from {password, TOTP, synced passkey, recovery code}, so the next step asks for one of the others (a remembered device skips it, §0). Sessions record each factor used and `authenticated_at`.
- **Setup with a hardware passkey (extends 6a W7):** the first owner may register with a hardware passkey instead of password + TOTP; a synced result is refused there ("use a security key, or a password and an authenticator app"), because the first owner must be able to sign in alone. The backup-way rule of question 1 applies.

### 3.5 Challenges
`auth_challenges` (additive): sha256 of the (pre-)session id, purpose (`register` / `login` / `factor` / `stepup` / `setup`), user (when known), the challenge, the UV requirement, created, expires (5 min), used at. A new `begin` for the same session and purpose replaces the open one. `finish` claims the row in one `UPDATE … WHERE used_at IS NULL AND expires > now` inside its transaction, so a replay or a second tab loses; the session id must match the one that began it (a challenge can't move between sessions). Rows are deleted after a day.

### 3.6 OIDC login (P5)
- **Settings** (section "Auth & sessions", owner-only, high-impact, D-075 explanations): `auth_oidc_enabled` (off), `auth_oidc_issuer`, `auth_oidc_client_id`, `auth_oidc_client_secret` (write-only, encrypted), `auth_oidc_label` (the button text), `auth_oidc_scopes` (default `openid profile email groups`), `auth_oidc_groups_claim` (`groups`), `auth_oidc_group_map` (§9.4), `auth_oidc_required_amr` (question 2), `auth_oidc_backchannel_logout` (on, §9.5). Saving them runs discovery once and refuses a provider whose metadata fails validation, whose `issuer` differs from the setting, or that offers only symmetric or `none` ID-token algorithms. The redirect URI to register at the provider is shown: `<AFCLAUDE_PUBLIC_URL>/auth/oidc/callback`.
- **Begin** (`auth/oidc/begin`, public, write guard + the pre-session's CSRF token; purpose `login`, `link` (signed in, step-up) or `stepup`): stores an `oidc_flows` row (sha256 of `state`, the pre-session, `nonce`, the PKCE S256 verifier, purpose, user for `link`/`stepup`, a `return_to` that must be an app path from a fixed list, created, expires 10 min, used at) and returns the authorization URL (`response_type=code`, `code_challenge_method=S256`, `prompt=login` + `max_age=0` for step-up).
- **Callback** (GET, `BROWSER_ROUTES`): the flow row by `state` and the same pre-session cookie (`SameSite=Lax` sends it on this top-level navigation), claimed single-use; RFC 9207 `iss` when the provider supports it; the code exchanged (client_secret_basic, the verifier); the ID token verified with the JWKS (signature, alg from the allowed list, iss, aud, azp, exp, iat with 60 s leeway, nonce; for step-up `auth_time` must be after the flow began); `amr` per the setting; groups from the ID-token claim, else from userinfo (whose `sub` must match). Then, in one transaction: find or create the user by (issuer, sub) (`identities`, additive: user, issuer, sub, display e-mail and name, created, last login; e-mail never links, §9.3; a new identity = a new person user, username from `preferred_username` with a suffix on collision, display only), `grant.sync_groups` (5a) with the groups, a new full session (rotated id, factor `oidc`, the ID token's `sid`), audit. Any failure: no session, an audited refusal, a redirect to `/login?error=<fixed code>` (never the provider's text).
- **Owner through a group:** a login whose group sync newly grants `owner` raises an alert to the owners (§9.4's warning is on the group-map setting itself). A login with no matching group = registered, no access (D-149).
- **Linking** (F11, signed in, step-up): purpose `link` attaches (issuer, sub) to the signed-in user if no one has it; unlinking needs step-up and is refused when it would leave the user with no complete way to sign in.

### 3.7 Back-channel logout (P6)
`POST /auth/oidc/backchannel-logout` (`BROWSER_ROUTES`, public, form-encoded `logout_token`, outside the JSON write guard: it is server to server and carries no cookie). The token is a JWT verified with the provider's JWKS: iss, aud, iat (within 5 min), `jti` not seen before (kept 1 day), the back-channel event in `events`, `sid` and/or `sub`, no `nonce`. It ends that `sid`'s sessions, or every session of (issuer, sub). 200 on success, 400 otherwise, `Cache-Control: no-store`, rate-limited per IP. Not every provider sends it (Authentik does since 2025.8; Authelia doesn't yet): the settings page shows `backchannel_logout_supported` from the provider's discovery next to the setting. Without it, a removed user or group stays signed in until the session's idle or absolute limit; groups are re-read at every OIDC login (§9.4).

### 3.8 Step-up (P7)
- **Mechanism:** `Endpoint.step_up: bool` in 6a's table; the dispatcher checks, after the session, that `authenticated_at` is within `auth_reauth_window_min` (10), else 403 `step_up_required` (details: the methods this user has). The step-up endpoints themselves are exempt. 6b marks its own high-impact endpoints (passkey add/remove, OIDC link/unlink, password and TOTP change, recovery-code renewal, ending other sessions, every `auth_*` setting incl. the group map); 7b sets the flag on the rest of §9.5's list.
- **Methods** (never a remembered device, D-179 / §9.5): a hardware passkey (one ceremony, `auth/stepup/passkey/begin|finish`); two factors (password + TOTP / passkey / recovery code, `auth/stepup/factor`); OIDC with `prompt=login` and `max_age=0`, accepted only when the ID token's `auth_time` is after the flow began (a provider that ignores `max_age` fails the step-up with a clear message, not a quiet pass). Success rotates the session id and sets `authenticated_at`; it never extends the absolute lifetime.
- **Client:** on `step_up_required` the API client opens the re-auth dialog with the methods offered, then retries the write with the **same idempotency key**. The OIDC method opens the provider in a popup started by the user's tap; the callback page (`/auth/done`, app shell) posts "step-up done" on a `BroadcastChannel` (same origin; the popup has no opener, COOP same-origin) and closes; the dialog retries the write. If the popup can't open, the dialog says so and offers a full-page sign-in after which the action must be tapped again; the write is never retried without the user knowing.

### 3.9 Sessions, remember-device, recovery (P8)
- **Lifetimes:** 6a's settings (§9.5) for every login method; OIDC sessions don't follow the provider's session (a provider logout reaches AFClaude only through §3.7). `auth_max_sessions_per_user` counts every method.
- **Remember-device** (6a builds the cookie and table): it skips only the second factor after a password or a synced passkey (§0); never a first factor, never step-up, never the setup; revoked on any factor change (password, TOTP, passkey added / removed / disabled, recovery codes renewed) and listed in F11 with "sign out".
- **Recovery codes** (6a): one factor, never alone. Renewing them (F11, step-up) voids the old ones. An account whose only way in is passkeys is covered by question 1.
- **Lockout:** `afclaude admin reset-auth` (6a) also removes the user's passkeys, pending challenges and OIDC links; an owner resets another user's factors through `auth.reset_user` (owner, step-up, audited, alerted; the button comes with 7b's users page). The last-owner guard (D-183) is 5a's and is not touched by a reset (the user stays owner, only the factors go).

### 3.10 Rate limits
On 6a's `auth_failures` and its client-IP rule: every failed `finish`, factor, step-up or callback counts against the account when known and the IP (§9.5: 5 / 15 min per account, 20 per IP, then exponential backoff; repeated failures alert). `begin` calls (passkey and OIDC) are limited per IP (30 / min) and one open challenge per session and purpose (§3.5), so the challenge tables can't be flooded. The back-channel endpoint: 60 / min per IP.

### 3.11 TS client (P4, P7, P8)
- `src/auth/webauthn.ts`: base64url ↔ `ArrayBuffer`; the server's creation / request options (typed by the generated types) → `navigator.credentials.create()` / `.get()` → the exact response shapes the server's models accept. It decides nothing; `NotAllowedError` (cancelled or timed out) and `InvalidStateError` (this key is already registered) become UI states, not requests.
- Views: login (passkey button, "<label>" OIDC button when configured, username/password), the second-factor step offering a passkey, the synced-passkey warning and confirm dialog, setup's hardware-passkey option, the re-auth dialog, F11 (passkeys with a hardware / synced badge and the reason on its tooltip, rename / remove, add; TOTP; recovery codes; OIDC link; active sessions and remembered devices with "sign out"; display time zone).
- Nothing auth-related in web storage (§9.8); the CSRF token stays in memory; WebAuthn calls carry it like every write.

## 4. Order and dependencies

- **P1** (MDS) and the pure parts of **P2** (classification and assertion rules over fido2's types, with the soft authenticator) have no dependency and can start now; their tables and actions (`mds_cache`, `passkeys`, `auth_challenges`, the `users` handle column) go through `store.py` / `actions.py`, which the held 3a branches also change, so they land after the 3a merge, one step at a time.
- **P3** needs 6a W5 (sessions, CSRF token), W6 (login, the factor rule) and W7 (setup), and 5a A1 (`users`). **P4** needs 6a W3 (TS scaffold) and P3. **P5** needs 6a W5 and 5a A1 (`grant.sync_groups`, the last-owner guard) and the master-key loader (5b or 6a W6). **P6** after P5. **P7** after P3 and P5 (OIDC step-up). **P8** after P3, P5, P7 and 6a W8. **P9** last.
- Nothing of 6b is deployed before 8b (D-072 / D-157). Real authenticators (security keys, Windows Hello, phones, password managers) are first tried on the 8b deployment; until then the unit tests use recorded and generated attestations.

## 5. Steps

**P1: MDS3 fetch, verify, cache.**

## 6. Questions for the owner

1. **A second way in for accounts that sign in with a security key only.** You can make an account whose only login is a hardware security key (no password, no authenticator app). If that key is lost or breaks, that person can't sign in any more: the one-time recovery codes only work together with another login factor, by design. For an owner, the remaining way back is a command on the server; for everyone else, an owner can reset their login. Options: (a) owners must add a second way in before their setup is finished (a second security key, or a password plus an authenticator app); other users only get a warning, since an owner can reset them; (b) everyone gets a warning only, nobody is forced; (c) everyone must add a second way in. Recommendation: (a): an owner locked out of every way in can only come back through the server's command line, while other users have an owner to help them.
2. **Whether AFClaude should insist that your login provider (e.g. Authelia or Authentik) asked for a second factor.** When someone signs in through the provider, AFClaude trusts the provider's check completely. The provider can tell AFClaude whether it asked for a second factor (a code or a security key), and AFClaude can refuse sign-ins where it didn't. This matters most when a group at the provider makes someone an owner. Options: (a) require it for every sign-in through the provider; (b) require it only when the sign-in gives owner rights; (c) don't require it (the provider's own rules decide). Some providers don't report this; then the required sign-ins would be refused until it is switched off, and the settings page shows what your provider reports. Recommendation: (b): owner rights control everything, and other users' rights are limited to their projects.
