# Prompts

Every prompt AFClaude sends lives here, so the dashboard can show and edit them later. These files are the defaults. `prompts.py` is their registry (phase 4a): each file's variables (system ones the sender fills, per-project ones a project's values fill, D-197) and its senders; every sender loads them through it, and `test_prompts.py` keeps the registry, the files and this table in step.

| file | used for | placeholders |
|---|---|---|
| `continue.md` | continue message for a resumed AFClaude session: the task-manager at a session-window start or last-stretch slot start (keepalive.py), an approved stalled session in the AFClaude repo (dispatcher.py) | `{reason}`, `{progress}` |
| `fillup.md` | the fill-up run (D-212): continue message for the task-manager shortly before the session reset of a session window whose run stopped early (keepalive.py fillup_pass) | `{reason}`, `{progress}`, `{remaining}`, `{reset}` |
| `last_mile.md` | the continue message of a last-stretch slot start (keepalive.py, the slots before the weekly reset): the remaining weekly quota would expire unused | `{reason}`, `{progress}` |
| `run_pace.md` | D-274/D-275: inserted after the continue of every start (session-window start, planned or postponed start, last-stretch slot, fill-up; keepalive.run_pace_text): pace the work to fill the session window and finish only within its last hour | `{end}`, `{last_hour}` |
| `run_chain.md` | D-274: follows `run_pace.md` when the next start comes right at this run's end (fillup.chained): keep going about an hour into the next session window once its continue arrives, so the prompt cache stays warm | `{next}`, `{until}` |
| `session_end_save.md` | the save prompt right before a compaction (D-144/D-233/D-238, design §5.5): typed into the task-manager when the watcher compacts it (a run ended, 50 min idle, or mid-run above the threshold, D-307), before the `/compact` (keepalive.py save_before_compaction); the keep-alive waits for the new hand-off in the DB (only one written after the prompt counts); it asks for the D-305 fields too: the owner's messages verbatim, in flight (with each background subagent's agent id, task and branch: a mid-run compaction goes on while they work, D-307), lessons, working notes | `{why}` (keepalive.TRIGGER_TEXT), `{session}`, `{tasks}` |
| `session_end_save_retry.md` | the save prompt re-sent once when the session answered `session_end_save.md` without a new hand-off (e.g. pointing at one it wrote before the prompt): says no new hand-off was found; a second reply without one fails the compaction (D-233/D-234/D-235, keepalive.save_retry_text) | `{newest}` (the newest hand-off from before the prompt, `#N` or `none`), `{session}`, `{tasks}` |
| `session_end_save_refresh.md` | D-307: the hand-off asked for again before the `/compact` when something reached the session after it was written (a background subagent's task notification, the owner's message; keepalive.refresh_stale_handoff, at most 3 times, then the compaction fails) | `{handoff}` (`#N`, the out-of-date one), `{what}` (what arrived, and when), `{session}`, `{tasks}` |
| `compact.md` | the instruction after `/compact` when the watcher compacts the task-manager (keepalive.py compact_session); the standing rules are left out of the summary, the SessionStart hook loads them again (D-225) | — |
| `compact_resume.md` | the hand-off the session saved right before the compaction (`handoffs`, rendered by store.render_handoff; with its D-305 fields: the owner's messages verbatim, in flight, lessons, working notes), given back to it inside `compact_after.md`. There is no fallback text: without that fresh hand-off the compaction is an error and automation is paused (D-234) | `{when}`, `{handoff}`, `{progress}` |
| `compact_after.md` | D-238: the message right after the compaction, with `compact_resume.md` in `{resume}`: the session takes the hand-off back and answers "READY" without starting work (no run is going); the keep-alive then marks the hand-off consumed | `{resume}` |
| `compact_after_run.md` | D-307: the message right after a mid-run compaction (the context passed `compaction_threshold_tokens` during a run), with `compact_resume.md` in `{resume}`: the run goes on with the hand-off's next steps, under the run's budget and pacing (keepalive.mid_run_text: from the run's fire record and the budget evaluated now) | `{resume}`, `{threshold}`, `{started}`, `{reason}`, `{budget}`, `{pace}` (`run_pace.md` + `run_chain.md`) |
| `project_start.md` | first message of a new project session (`--work-on`, retired in 3b S5; unused, S6 removes it) | `{title}`, `{desc}`, `{slug}` |
| `manager_first_start.md` | phase 3b S4 (D-281): the first message of a project's new task-manager session, created at the project's first start (keepalive.create_task_manager, `--new` in the project's path); the description is the one-off kickstart (D-301) | `{project}`, `{path}`, `{desc}`, `{progress}` |
| `run_project.md` | D-301: the project's current name, in every start's / slot's / fill-up's continue to a task-manager (keepalive._fire_start) | `{project}` |
| `continue_foreign.md` | neutral continue message for an approved stalled session that is not an AFClaude session (dispatcher.py; the user's own sessions get only this + `guard_respect.md`, and resume on their own model). (`{context}` is empty since D-205: task sessions and task-managers are never continued at a limit reset, D-204) | `{reason}`, `{context}` |
| `task_start.md` | first message of a task session; unused since D-205 (the dispatcher starts no task sessions, a project's task-manager works its tasks), kept for design phase 3b | `{id}`, `{title}`, `{project}`, `{description}`, `{qa}` |
| `guard_respect.md` | a standing rule: respect the guard hooks even when they're bypassed. Appended to every session message (the user's own sessions: only this), except where the SessionStart hook loads it (below) | — |
| `manager.md` | a standing rule for all but the user's own sessions: act as the project's task-manager and delegate to subagents; names the project's progress notes through its project variable (P5; AFClaude's value is PROGRESS.md) | `{progress_location}` (project variable) |
| `manager_project.md` | phase 4a P3 (D-197): the generic task-manager template, a standing rule after `manager.md` for every project (it replaced `manager_afclaude.md`): usage report, the clean session stop, goal list and questions, the project docs, budget, D-204/D-219/D-224, nightly tasks. The project's own lines are its prompt variables (`prompts.py vars`): `{goals_location}`, `{progress_location}`, `{questions_location}` and the whole lines `{public_repo_rule}`, `{worktree_rule}`, `{project_notes}`, `{docs_rule}`, `{deploy_rule}` (an empty one leaves no line); AFClaude's values are seeded by `prompts.py migrate`, a second project's are its own or the defaults | `{session_stop_pct}` (the setting, D-014), `{afclaude_dir}` (the install directory), `{tools}` (the prefix of its commands: empty in this checkout, else the install directory) + the project variables |
| `afk_rules.md` | a standing rule after those: the AFK rules for unattended runs (nobody at the keyboard, guards off but respected, no destruction, exceptions in EXCEPTIONS.md, Berlin time); formerly only in the first message | — |
| `session_rules.md` | D-225: the header of each part the repo's SessionStart hook injects (`keepalive.py --session-rules manager` = `manager.md`; `… afclaude` = `manager_project.md` filled with AFClaude's own values + `guard_respect.md` + `afk_rules.md`) at session start, on resume and after every compaction, for sessions started in the repo root. Two parts: Claude Code caps each hook's context at 10,000 characters | `{part}`, `{what}` |
| `rules_pointer.md` | D-225: replaces the standing rules in session messages to a session started in the repo root (they come from the hook): one line pointing at them. Sessions elsewhere get the four rule files inline instead (`manager_project.md` with their project's values) | — |
| `usage_review.md` | the periodic usage-model review (usage_review.py): the monthly one is a nightly task (D-254: a worker subagent of a nightly run, its brief `nightly_tasks.py brief <name>` = `nightly_task.md` + this + `stage_eta_review.md`), a one-off one its own session (Opus, medium effort); one review that tests hypotheses, sorts findings into universal (code, public) vs user-specific (the user model in the DB, `telemetry.py user-model`, local) and leaves an unread-review note in memory. Reused verbatim for a one-off usage review (`usage_review.py --only usage`/`usage,stage-eta`, D-228): same brief, just logged outside the monthly schedule | `{date}`, `{since}` |
| `stage_eta_review.md` | appended to `usage_review.md` in the same monthly review (its nightly task's brief): the rare stage-ETA review (D-213) that scores the logged stage ETAs (`stage_eta.py --score`) and tunes the stages' session estimates only (D-142 analogue) | `{date}` |
| `stage_eta_review_once.md` | a one-off stage-ETA review outside the monthly schedule (`usage_review.py --only stage-eta`, D-220/D-221), with its own extra brief instead of `stage_eta_review.md`; also a nightly task's prompt (the D-261 re-run) | `{date}`, `{report}` (the review doc) |
| `stage_eta_review_once_after_usage.md` | inserted ahead of `stage_eta_review_once.md` only for the chained one-off (`usage_review.py --only usage,stage-eta`, D-228): points the ETA review at the SEPARATE one-off usage review session's result instead of re-deriving it | `{report}` |
| `inbox_triage.md` | D-241: Haiku sorts an owner message from the dashboard's message box (inbox_worker.py): `now` (needs a direct response) or `note` (waits for the next start); JSON answer | `{text}` |
| `inbox_now.md` | D-241/D-186: a "now" message typed into the task-manager at once (inbox_worker.py), with its id (`[AFClaude inbox #id]`, checked in the transcript) and how to answer (`tasks.py inbox reply`); a resumed session also gets the standing rules / the hook pointer | `{id}`, `{at}`, `{text}`, `{notes}` |
| `inbox_notes.md` | D-241: the noted owner messages, verbatim, appended to the next message into the task-manager (a start's continue / fill-up, the post-compaction message in `{resume}`, a "now" message's `{notes}`); they are then marked included | `{notes}` |
| `nightly_tasks_due.md` | D-254/D-261: one line in a night start's continue (not a last-stretch slot or a fill-up; only the task-manager in this checkout) naming the due nightly tasks (`nightly_tasks.start_insert`): run each as one worker subagent with `nightly_tasks.py brief <name>` | `{tasks}` |
| `nightly_task.md` | D-254: the head of every nightly task's brief (`nightly_tasks.py brief`): a worker subagent inside a nightly run's budget; write the report doc only once the whole task is done (that marks it done); out of budget: stop and report, the next nightly run brings it again | `{name}`, `{title}`, `{report}` (+ the task's fields) |
| `stage_eta_review_rerun.md` | D-261: appended to `stage_eta_review_once.md` in the nightly task of the ETA review's re-run a week on: the owner's words, start from the first run's results, measure again with `stage_eta.py --split`, say what changed | — |
| `compaction_handoff_review.md` | D-305: the one-off nightly task a week after the hand-off got owner_messages / in_flight / lessons / working_notes: pair each compaction summary with the hand-off written just before it, find what was used after the compaction that only the summary held, the cost numbers, and recommend compaction or hand-off + /clear (asked as a question in the DB) | `{date}`, `{report}` |
| `inbox_held.md` | D-244: the "now" messages still held (the owner held the session, a usage limit, ...) go out with the next start's message (`keepalive._fire_start`), each with its `[AFClaude inbox #id]` marker (checked in the transcript) and how to answer (`tasks.py inbox reply`); they are then marked delivered | `{held}` |
| `usage_haiku.md` | per-session usage classification by Haiku (usage_sampler.py) | `{name}`, `{n}`, `{prompts}`, `{gaps}`, `{totals}` |

Session messages are flattened to one line (tmux send-keys). Literal braces in a file with placeholders must be doubled (`{{ }}`).

**The project docs (dashboard phase 2d part 2, design §7.7).** PROGRESS.md, GOALS.md, EXCEPTIONS.md, ALERTS.md and the review reports are docs in the DB (`project_docs.py`); the DB is the source. `manager_project.md` (its `{docs_rule}`) and the review prompts (`usage_review.md`, `stage_eta_review*.md`) write through the write path (`tasks.py doc append progress "…"`, `tasks.py doc set goals -`, `tasks.py doc set review:<date> -`, MCP `afclaude_doc`), and the AFClaude task-manager runs `tasks.py doc export` (the only file output, D-181) before each commit of the build log. Hand edits of PROGRESS.md / GOALS.md / EXCEPTIONS.md stay valid (the generic prompts, `{progress}`, `afk_rules.md`, `guard_respect.md` still name the files): a scheduled import (every 10 min) merges them into the DB with the runners' notes.
